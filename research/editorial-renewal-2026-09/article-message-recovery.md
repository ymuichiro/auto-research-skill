# 記事別メッセージ回復台帳

作成日: 2026-09-20

## この台帳の目的

今回の改稿では、根拠のない市場一般化を取り除く過程で、多くの記事が「確認できる仕様を一つ示し、運用上の注意を添える」同型の文章になった。その結果、旧稿にあった読者への問い、比較の軸、著者の判断まで縮んだ。この台帳は、旧稿の強い言い回しをそのまま戻すためのものではない。旧稿が読者に何を理解させようとしたかを復元し、その判断を事実・具体例・留保で支え直すための設計図である。

各項目の「旧稿」は、各記事の実質的な改稿コミットの親版を読み、見出し、結論、例示、出典の役割から再構成した。「追加する根拠」に挙げた資料名は、旧稿の調査目録にあった一次資料・論文を中心にした候補である。**再改稿時には記事の日付以前に公開された版か、資料が実際にその主張を支えるかを一件ずつ再検証する。** ここで資料名を挙げたことは、旧稿の主張を現在確認済みの事実として復活させることを意味しない。

文字数は HTML を含むファイル文字数であり、増量の目標値ではない。削った分を同じ量だけ戻すのではなく、読者の判断に必要な説明だけを、証拠に沿って戻す。

## 再改稿の共通規則

1. 各記事は、タイトルで約束した一つの問いと一つの暫定的な答えから始める。製品の列挙、一般論、運用チェックリストを先に置かない。
2. 本文は「確認できる事実 → その事実が見える具体的なケースまたは測定条件 → 比較・仕組み → 本稿の解釈 → 成り立たない条件」の順で進める。著者の解釈には「本稿では」「この比較からは」など、資料の記述と区別できる主語を付ける。
3. ベンチマークは、モデル名、タスク、測定指標、環境または版、比較対象を一組で書く。製品文書は、提供機能、提供範囲、利用者が残して定義する部分を分ける。
4. 仮想例は、仕様や研究結果の働きを説明するためだけに使い、「想定例」と明記する。実在導入や性能実績のようには書かない。
5. 日英版は、根拠の強さ、条件、著者の解釈を対応させる。英語版を短い要約にせず、同じ論証の別言語版にする。
6. 再改稿は一記事ずつ行う。各記事で、一次資料を 20 件以上集め直して採否を記録し、日本語・英語・メタデータを同時に更新し、表示と出典リンクを確認してから次へ進む。

## 記事別回復計画

### 2025-01-01 — agents-shift-to-measurable-systems

**旧稿の読者への約束。** AI エージェントの話題が、印象的な対話デモから、道具・環境・採点条件を含む「測れる仕事の設計」へ移った理由を示す記事だった。

**戻すべき判断。** 「ツールを呼べる」ことと「境界付きの仕事を完了できる」ことは別であり、後者を測れる環境が設計議論を具体化した、という歴史的な読みを残す。市場全体が一斉に移行したとは書かない。

**追加する根拠と具体例。** ReAct の Thought/Action/Observation の往復、Toolformer の API 利用、WebArena の状態を持つ Web タスク、SWE-bench の issue・patch・test という三つの異なる完了条件を短く比較する。WebArena の成功率を示すなら、論文のタスク、エージェント、指標、版を併記する。想定例として「検索 API を一度呼んだ」操作と「注文の条件を保ったまま変更を終えた」仕事を対比する。

**組み立て。** まず「何が測定対象になったか」を三例で示し、次にツール呼び出しと最終状態を分け、最後に本稿の解釈として「評価可能な仕事境界が実装の比較単位を変えた」と結ぶ。現行のタスク試験の説明は後半の実践節に残す。

## 実施順と各記事の完了条件

この台帳は優先順位の代わりに使わない。日付順に、一記事ずつ次を完了してから次へ進む。

1. 旧稿の見出し、結論、出典目録を再読し、この台帳の「旧稿の読者への約束」を、タイトルと導入の一文に落とす。
2. 一次資料・論文を 20 件以上集め、記事の日付との整合、本文で使う箇所、使わない理由を調査メモに残す。
3. 事実、比較から得る観察、本稿の解釈、想定例、未解決条件を区別した論証図を作る。
4. 日本語・英語本文と meta.json を同時に書き直し、見出しごとに中心問いへの寄与を確認する。
5. 出典リンク、表示、構造化データ、日英の意味対応を確認し、公開後のページを読み返して初めて次の記事へ進む。

この完了条件により、長さを戻すこと自体を目的にせず、記事固有の問いと、その問いに答える証拠・比較・具体例を回復する。
