# エージェントIDと委任の記事の改稿記録

## 問いと論証

対象日2026年3月26日。旧稿と現行の日英本文/meta通読。
問い: エージェントを識別できるようになった後、誰のどの権限を渡し、必要な仕事を止めずに一つの委任を取り消すには何を確かめるか。
判断: 専用IDは管理と調査の単位になるが、利用者の閲覧範囲、接続先の許可、発行済み認証情報、取得済み資料の扱いまで自動で解決しない。エージェントと利用者、接続先、停止対象を結び付け、権限の取得から変更/失効まで実経路で検証する。
Coworkの複数成果物の整合から、委任権限とその有効期間と取消へ進める。旧稿の主体/委任/認証の受け渡し/管理責務の幅を回復し、サービスアカウントの普遍的不足、五社等価、最適用途/速度/構造的優位の断定は回復しない。

| 論点 | 根拠と想定例 | 解釈と限界 |
| --- | --- | --- |
| 依頼とアクセス | 想定文書検索、担当者による可視範囲差と共有 | 入口で認証しても下流/キャッシュが利用者範囲を保つとは限らない |
| IDの管理単位 | BuildMay19 unique IDs preview; IgniteNov18 inventory/lifecycle preview | 名前・登録・所有者が、権限の付与/停止/調査で使えるかを見る |
| 専用と委任 | AWSJuly16 workload/consent; Auth0Oct9 token vault | 管理者の定期処理と利用者委任を分ける。外部refreshをモデルへ渡す必要がない構成と、権限を適切に絞ることを区別 |
| 接続先の認可 | MCPNov25固定原文、audience/passthrough/optional/HTTP/STDIO | 入り口とAPIの別トークン、正当な発行と業務の対象を別に判断 |
| 四つの問い | 実行主体/委任者/対象操作/説明記録 | 本稿の分解であり万能token方式ではない。記録に秘密を残さない |
| 変更と取消 | RFC7009 revocation/伝播/refresh対access;担当交代の想定 | UI切断や削除で全経路即時停止とは言わない。既取得のファイル/記憶も別の処理 |
| 他の検査 | PolicyMar3 Gateway outside code; 正常権限でも誤要約 | ID、操作の認可、出力検査の対象が違う。動作する認可範囲を確認 |
| 試行と人 | 二利用者、無効化、正当な検索/禁止閲覧/送信、通常業務と限定停止 | 許可の広さより、必要な仕事の継続と対象だけ止まること。製品実測の結果ではない |
