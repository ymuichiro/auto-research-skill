# Agent SDKの記事の改稿記録

## 問いと論証

対象日: 2025年10月1日。旧稿と現行の日英本文、metaを読んだ。
問い: コーディングで使った実行ループを業務へ移すとき、どこをAIの探索に任せ、どこを固定するか。
判断: 再利用するのは観測に応じて手順を変える仕組み。業務定義、計算、出力条件は組織が定めた道具と処理へ置き、反復がその条件を緩めない構成にする。
9月の実験比較、8月の復旧と重複、7月の接続交換とは分け、実装内の適応処理と固定処理の分担を中心にする。旧稿のSDK汎用化、文脈、道具、複数製品の広がりを回復し、業種の羅列と普及の断定を外す。

| 論点 | 根拠・例 | 判断と限界 |
| --- | --- | --- |
| 反復の再利用 | Claude SDK Sep29 rename、file/command、gather-act-verify | 用途例は全業務の成功証明ではない。観測から手順を変えられる価値 |
| 道具を業務の単位で設計 | Anth tools Sep11 search vs list、customer context | 任意SQLや全データより必要な対象・定義を渡す。複合道具は障害/欠落を隠さない |
| 計算の意味を外部定義へ | Looker Aug9 defined metrics/generated SQL | 指標を選ぶ理由と適合性の判断は残る。版情報はアプリ提案で既定API保証ではない |
| 検証の深さ | Firestore Sep18 Alex20stagingaccounts/semicolon hypothetical | 構文正常は条件を守ることの検証ではない。時間改善は測定値にしない |
| 固定処理と適応の共存 | MS Oct1 Agent vs Workflow Orchestration | 接続/共通runtimeの予定と現在の説明を分け、他SDK同機能とはしない |
| 月次報告の段階 | 著者想定: returns missing、approved metric、fixed recalc、exception clarification | 不足は0とせず停止、固定条件をAIが変えない。根拠付き限定レビューへ |
| 使わない判断 | Effective agents Dec19,著者固定CSV処理との比較 | 全手順既知ならscript;同入力の固定処理が必要な箇所へ反復を増やさない |
