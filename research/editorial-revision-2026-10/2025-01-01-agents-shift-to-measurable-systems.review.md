# 測定可能な仕事の記事の改稿記録

## 問いと論証

対象日: 2025年1月1日。旧稿と現行の日英本文、メタデータ、前回の縮約記録を確認した。
問い: 道具を使ったデモが成功しても、なぜ利用者の仕事の成功を示したことにはならないのか。
判断: 行動の選択、観測の利用、環境に残った最終状態を分け、失敗した場所を読める採点条件を作る。型番の違う保守期限を答える想定例を、冒頭から結論まで使って違いを示す。
市場全体が一斉に移行した、特定領域が最も導入しやすい、任意の5〜10件で評価すれば十分という旧稿の断定は回復しない。

| 論点 | 具体的な根拠 | 比較と限界 |
| --- | --- | --- |
| 道具を選ぶ仕組みには異なる研究課題がある | ReAct v3、Toolformer v1 | 推論と観測の往復と、API呼出しを学習へ取り込む方式を同じ性能指標で順位づけしない |
| 検索を加えても全課題が改善するわけではない | ReAct v3 Table 1、PaLM-540B | HotpotQA完全一致率27.4対CoT29.4、FEVER正解率60.9対56.3。課題と尺度を保持 |
| Web操作の成功は最終状態で測る | WebArena v2 | GPT-4ベース14.41、人78.24は当時の環境固有の完了率。自社や現在のモデルへ転用しない |
| コード生成と問題解決は違う | SWE-bench v1 | 実際のIssueと対応PR、12リポジトリ2,294件。試験への合格と未測定の品質を区別 |
| 画面の操作と保存結果も違う | OSWorld v1 | 369課題、初期状態と実行ベースの判定器。OS対応と全OSでの同一性能を混同しない |
| インターフェース統一は課題の同一化ではない | BrowserGym v1 | 共通の観測・行動空間と実験管理を提供。異なる課題の点数を万能順位へ変えない |
| 製品の部品は完了条件を実装する足場になる | 2024年AWS、Google、Anthropicの発表 | 機能の存在は導入成果の証明ではない。APIの成功、取得情報の適用、最終回答を別々に確認 |
| 人が誤りを直せる評価へする | 保守期限の著者想定例 | 型番、契約、版、不足情報、外部変更を課題に含める。未知を全件返すだけの方式も区別 |

## 調査

既存28候補のURLを確認した。2件のOpenAI発表は直接取得が拒否され、本文では使わず確認済み数にも含めない。対象日以前の一次資料は26件。
Mind2WebとAutoGenの日付は元のカタログから原版の公開履歴へ訂正。WebArenaは14.41%と78.24%を確認したv2へ固定し、版の公開日を2023年10月24日として保存。現在の未固定URLで後年の結果を混入させない。
ReAct v3のTable 1を直接確認し、外部検索の有無だけで全課題の改善を断定しない。Toolformer、SWE-bench、OSWorld、BrowserGymは原版の課題と評価対象を確認。公開資料は本文の論点へ必要なものを選び、候補数を引用ノルマにしない。
