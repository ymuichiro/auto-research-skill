# 全記事の日英改稿に共通する修正計画

作成日：2026年10月3日。
対象は、今回分析した公開済み36記事の日本語版と英語版、計72本文、および各記事のメタデータである。

この計画の目的は、根拠を慎重に扱う姿勢を維持しながら、短縮で失われた背景、比較、仕組み、反論、著者の判断を回復することである。
読者が無理なく読み進め、読み終えたときには、対象の技術や仕事をどう考えるかが変わる記事を目指す。
簡潔さは文の表現と重複の整理で実現し、論証に必要な説明の省略で実現しない。

ここでは全記事に共通する確認事項、判断条件、修正方針、完了条件を定義する。
記事ごとの独立したゴールや新しい作業単位は作らない。
実施時は一記事の日英版とメタデータを一つの単位として、確認、修正、再確認を終えてから次へ進む。
実施状況：本計画に従い、36記事の日英72本文とメタデータの改稿、原典照合、通読、生成と表示の確認を完了した。今回の実施では、全記事の確認後にまとめて公開し、全72記事の公開本文・HTTP応答・主要メタデータの一致も確認した。結果は[進捗台帳](../editorial-revision-2026-10/progress.json)と[公開検証記録](../editorial-revision-2026-10/public-verification.json)に記載。

## 共通のゴール

全記事で、次の状態を満たす。

1. 読者が冒頭から、この記事を読む理由と中心の問いを理解できる。
2. 確認した根拠を比較し、なぜその違いが生じるかを説明した上で、著者が何を判断したかが伝わる。
3. 読者が判断に必要な背景、仕組み、具体例、代替案、成立条件まで理解でき、出典の要約だけでは得られない説明がある。
4. 平易な文章で読み進められ、結論に至る途中の論理が切れない。
5. 事実、ベンダーの自己申告、研究の測定結果、著者の解釈、想定例、未確認事項を区別できる。
6. 日本語と英語のどちらを読んでも、同じ問い、判断、根拠、留保、実務上の含意に到達できる。
7. タイトル、要約、本文、引用、関連記事への案内が同じ内容を約束し、検索や一覧から来た読者が目的の記事か判断できる。

Googleでの登録や上位表示は、この共通ゴールに対する外部の結果として観測する。
検索に出たことを文章の正確さの証明にせず、検索に出ないことだけで改稿を不合格にもしない。

## 修正前に確認する視点

各記事では、旧稿、現行の日英本文、メタデータ、近いテーマの記事を読む。
前回の分析表は確認箇所を見つける参考に使い、個別の修正案を検証せず採用しない。

| 視点 | 共通の確認事項 | 修正に使う判断 |
| --- | --- | --- |
| 読者の疑問 | 誰がどの場面で何に迷い、読後に何を理解したいか | 導入を具体化し、その疑問に答えない話題を整理する |
| 元の記事の意図 | 旧稿の中心の問い、メッセージ、説明の広がりは何だったか | 根拠を再確認した上で、失われた問いと論証を回復する |
| 対象の変化 | 従来の方法と何が変わり、何が引き続き必要か | 新規性を機能名や発表の数で代用しない |
| 差を生む仕組み | 入力、処理、保持する情報、出力、変更可能な対象のどこに差があるか | 比較の理由を、具体的な挙動や研究条件まで掘り下げる |
| 実際の根拠 | 仕様、実装、研究の測定、導入の自己申告は何を確認できるか | それぞれが裏付ける範囲を限定し、想定例と分ける |
| 代替案と反論 | 手作業、固定手順、別方式ならどうなるか。結論が変わる条件は何か | 都合のよい比較だけで主張を作らず、選択の条件を示す |
| 人への影響 | 誰の作業、待ち時間、判断、修正負担、失敗時の負担が変わるか | 人に訴える部分を、具体的な仕事の変化として書く |
| 費用と実用性 | 時間、費用、導入負担、品質の違いは中心の問いに関係するか | 関係する項目だけを扱い、未測定の効率や成功率を作らない |
| 他の記事との関係 | 近い記事と比べて、この一本が答える固有の疑問は何か | 同じ承認手順や評価の一般論を繰り返さず、必要な箇所へリンクする |
| 読む順序 | 前の説明から次の疑問が生まれ、最後の判断へ進んでいるか | 章を増やす前に論証の欠落と重複を直す |

これらは編集時に検討する視点であり、すべてを本文の章として並べる条件ではない。
歴史、費用、権限、評価などは、中心の問いを変える場合に扱う。
不要な観点は内部の確認で理由を残し、記事へ無理に追加しない。

## 旧稿と現行稿をどう扱うか

旧稿の量を回復すること自体を目標にしない。
旧稿からは問い、比較の広がり、説明の順序を読み取り、現行稿からは引用の明確さ、条件の記述、想定例の区別を引き継ぐ。
必要な部分は前後を含めて組み直し、短い本文へ追記を積み重ねるだけの修正は避ける。

| 見つかった状態 | 修正方針 | 再確認の条件 |
| --- | --- | --- |
| 根拠があり、短縮で比較や仕組みが失われた | 説明と具体例を回復し、中心の問いにつなぐ | 追加した説明によって読者の判断が進む |
| 旧稿の断定が根拠の範囲を超えている | 根拠が支える範囲まで限定し、必要なら著者の仮説として再構成する | 観測と推論を区別し、結論が変わる条件を示せる |
| 主要な判断に必要な根拠が不足している | 原典を追加調査し、見つからなければ主張を狭めるか撤回する | 根拠不足を想定例や強い言葉で埋めていない |
| 注意書きが連続し、比較後の判断がない | 有効な留保を残し、比較から言えることを明示する | 読者が選べる案と選択条件が分かる |
| 一般論や同じ結論が繰り返される | 統合し、対象固有の挙動、研究条件、反例へ置き換える | 技術名を別のものに置き換えると説明が成立しなくなる |
| 想定手順が実在の根拠を置き換えている | 仕様や測定結果を先に説明し、想定例の役割を限定する | 想定例を実証済みの効果として読めない |
| 複数資料の結論が違う | 課題、版、比較対象、指標、測定条件を確認する | 差を説明できるか、未解決の違いとして示している |
| 表やカードが本文と同じことを繰り返す | 比較が見やすくなる部分だけ残す | 図表が独立した比較を助け、論証を分断しない |

中立性は、同じ条件で根拠を評価し、都合の悪い材料も扱うことで確保する。
必要な資料を比較した結果として、ある方式や設計を条件付きで勧めることはできる。
各社へ同じ紙幅を割くことや、すべての結論を曖昧にすることを中立性の条件にはしない。

## ストーリーと分析の深さを回復する

ストーリーは、読者が対象の見方を更新する順序として作る。
具体的な困りごとを示し、従来の方法がどこまで対応でき、どこで不足するかを説明する。
その不足へ答える根拠を比較し、仕組みと反例を理解した後に、著者の判断へ進む。
章立ては記事に合わせて選び、この順序を全記事の固定テンプレートにはしない。

主要な判断については、次の関係を本文からたどれるようにする。

**確認した事実や実例 → 差が分かる比較 → 差を説明する仕組み → 著者の解釈 → 読者への含意と成立条件。**

一段落へすべて詰め込む必要はない。
複数の段落を使っても、次の論点へ移る前に関係を説明する。
出典を列挙しただけの節、結論を繰り返すだけの節、中心の問いへ寄与しない節は統合または削除する。

読み応えを増やす際は、次の順に不足を探す。

1. 読者が比較の意味を理解するための背景が足りているか。
2. 何が違うかだけでなく、なぜ違うかを説明しているか。
3. 実在する仕様、実装、実験結果を具体的に説明しているか。
4. 同じ条件での代替案と、結論が変わる反例があるか。
5. 比較後に、著者が何を判断し、人の仕事がどう変わり得るかを述べているか。

反例や代替案は、実際に判断を変え得るものを選ぶ。
論争の演出や、形式を埋めるための反論は作らない。
架空の成功談、人物の体験、製品の導入効果も作らない。
根拠から言える限界を説明した後は、その範囲で何を選べるかまで進む。

## 根拠と対象時点を維持する

大幅改稿では、既存の情報収集ポリシーに従い、対象に関連する一次資料を20 URL以上確認する。
既存の調査目録は再利用できるが、URL、対象時点、現在確認できる記述、支える主張を再点検する。
同じ説明の別URLや無関係な文書で件数を埋めず、比較、反証、限界まで調べる。
20件は調査の条件であり、本文に載せる引用数や記事の品質点数にはしない。

公開根拠は、確認した公式文書、公式発表、論文、主張の一次情報となる公式リポジトリを使う。
ベンダーの資料から確認できる機能と、ベンダーが主張する性能や効果を区別する。
研究の結果を述べるときは、モデル、課題、版、比較対象、指標、時間や費用の条件、評価範囲を保持する。
複数資料の推論は、その比較と限界を示して著者の判断として書く。

本文の事実を引用する位置と`publishedSources`を対応させる。
本文だけにある根拠URLや、使っていない出典の羅列を残さない。
内部の調査目録には、採用した理由と採用しなかった理由を残す。

既存の月次記事や過去のスナップショットは、原則として記事が扱う対象時点の一次資料で論証を回復する。
継続更新される文書は、現在の記述から当時の機能を推定せず、版、公開日、履歴で確認する。
対象時点より後の情報を用いる場合は、後日の追記や更新として区別する必要性を判断し、過去から知っていたように混ぜない。

記事が扱う時点、実際の初公開日、実質的な更新日を区別する。
初公開日が不明な場合は、Gitへの追加日だけで確定せず、公開履歴を確認する。
共通の生成処理がこれらを区別できない問題は、記事本文の改稿と区別してサイト共通の修正として扱う。

## 読みやすさと日英の対応を確認する

日本語では、主語、行為、対象、条件、結果を追える文にする。
抽象語は、その中に何が含まれるかを説明してから使う。
一般的な工程は自然な日本語で書き、製品名、論文名、プロトコル名、API識別子は必要な表記を保持する。

段落は一つの理由や比較を進める単位にする。
一文段落を連続させて論証を細切れにせず、長い段落も複数の論点が混ざっていれば分ける。
内容と順序を確定した後に文の長短と段落の密度を整え、読みやすさの仕上げで根拠や条件を落とさない。

分量は、主要な分析記事を日本語本文4,000から7,000字、複雑な総説を6,000から10,000字程度から設計する案を採る。
これは説明不足を防ぐ編集上の目安で、最低字数やGoogleの要件ではない。
狭い問いに十分答えた記事は短くてもよく、必要な比較が多い記事は長くてもよい。
字数を合わせるための言い換え、無関係な歴史、同じ注意書きは追加しない。
仕上げの推敲後には、改稿前後の論点と本文分量を比べ、短くした箇所で必要な比較、根拠、成立条件が失われていないかを再確認する。
分量や残存率だけで合否を決めず、削除した説明の役割を他の箇所が引き継いでいるかを見る。

英語版にも、日本語版と同じ深さの背景、比較、反論、判断を残す。
日本語版を要約した英語版にはしない。
英語として自然になるよう文や段落を組み直しても、論証の機能を保持する。
両言語の文字数、単語数、段落数を機械的に一致させる必要はない。
英語版は単独でも通読し、日本語版を知っているから補える説明や、不自然な直訳が残っていないかを確認する。

日英の対応確認では、次の項目を照合する。

| 項目 | 一致させる内容 |
| --- | --- |
| 問いと結論 | 読者が理解する問題と著者の中心的な判断 |
| 比較と具体例 | 比較対象、条件、例が説明する仕組み |
| 数値と出典 | 数値、単位、分母、版、比較対象、参照先 |
| 主張の強さ | 事実、観測、推論、可能性、推奨の区別 |
| 限界と反論 | 未確認事項、成立しない条件、残る疑問 |
| 含意 | 誰が何を選べるか、人の作業や負担がどう変わり得るか |
| タイトルと要約 | 各言語で自然に書きながら、同じ内容を約束していること |

一方だけに断定、宣伝的な語、根拠のない補足が加わっていれば、両言語を再確認する。
一方で主要な説明が抜けていても、日英セットの改稿を完了としない。

## 検索と表示に共通する修正方針

タイトルは、対象とこの記事固有の問いまたは判断が分かる形にする。
連続する記事を同じ語尾へ揃えず、英語でも内容に合った自然な表現を選ぶ。
検索用タイトル、H1、要約、説明文が同じ内容を約束し、本文がその約束へ答えることを確認する。
検索語の候補は読者の疑問を考えるための仮説として扱い、未取得の検索需要を測定済みとして書かない。

関連記事へのリンクは、説明を深める位置に置く。
重なる説明は必要な概要を残して関連する記事へつなぎ、参照先にも固有の役割を持たせる。
キーワードの反復、答えていないFAQ、無関係な流行語、被リンクの数だけを増やす施策は採らない。

記事の更新では、現行URLを保つことを基本とし、内容の近さだけで削除、統合、リダイレクトを決めない。
日英のcanonical、hreflang、構造化データ、サイトマップ、公開日と更新日の表示を確認する。
著者や検証方法の説明には実際の関与と確認範囲を使い、未実施の利用体験や経歴を足さない。

ハブページ、編集者情報、日付の生成処理、アクセス計測はサイト全体の課題として管理する。
同じ共通修正を36記事で繰り返さず、一つの変更として検証する。
記事を一つずつ修正する途中で共通表示を変えた場合は、変更した表示に関係する既存ページも再確認する。

Googleの方針との関係は、独自の分析、十分な説明、読者への付加価値を増やすことにある。
字数や出典の数を増やしたことだけで検索改善を見込まない。
[Googleの読者を優先するコンテンツの説明](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)と[タイトルリンクの説明](https://developers.google.com/search/docs/appearance/title-link)を参照する。

## 一記事ずつ進める手順

全記事に同じ手順を適用する。
各記事の問いと論証は個別に設計するが、判断基準と完了条件はこの計画で共通化する。

1. **現状を確認する。** 旧稿、現行の日英本文、メタデータ、近い記事を読み、残す説明、回復する説明、撤回する主張を整理する。
2. **論証を設計する。** 中心の問い、著者の判断、必要な論点、比較、反論、読者への含意を作業メモに書く。
3. **原典を調べ直す。** 一次資料の目録を確認し、主要な主張の根拠、測定条件、対象時点、反証を記録する。
4. **日英を改稿する。** 内容を組み直し、両言語の本文と`meta.json`を同じ問いと判断へ合わせる。
5. **内容を再確認する。** 原典と本文を照合する確認と、冒頭から結論まで通読する確認を別に行う。
6. **日英の対応と表示を確認する。** 主要な論証を照合し、生成した両言語のページをPC幅とスマートフォン幅で読む。
7. **不足を修正して再確認する。** 次の完了条件に未達があれば、対象の調査、論証、文章、表示へ戻る。
8. **記録して次へ進む。** 日英セットの完了条件を満たしたことを記録する。公開する作業では配信内容も確認してから次の記事へ進む。

最初は前回の分析で回復余地が大きかった記憶の記事を候補とし、この共通基準を実際に適用する。
その結果で表現の基準や確認方法を調整しても、根拠と日英対応の基準は緩めない。
その後はUI、HACWを優先し、残りの記事も一つずつ処理する。
これは検索流入順の順位付けではなく、内容の回復余地による実施順の案である。

内部には一つの進捗台帳を置き、対象記事、作業段階、確認した版、修正理由、検証結果、未解決点を記録する。
個別の記事で独立したゴール管理は増やさない。
未着手の記事を先にまとめて書き換えず、日英の片方だけを終えて次へ進むこともしない。

## 全記事に共通する完了条件

次の条件を一記事の日英セットで満たしたときに、改稿完了とする。
条件を点数にして平均せず、主要な欠落を別項目の良さで補わない。

| 項目 | 合格と判断する条件 | 修正に戻る状態 |
| --- | --- | --- |
| 問いとメッセージ | 冒頭の問いと最後の判断が対応し、著者が何を伝えるかを本文から説明できる | 読む理由が不明、または注意事項の列挙で終わる |
| 論証の深さ | 主要な判断を、事実、比較、仕組み、解釈、条件までたどれる | 説明が概要や手順だけ、または一般論へ置換できる |
| 具体的な根拠 | 主要な事実が原典に対応し、測定条件と想定例の地位が正確である | 引用が主張を支えない、数値の条件が落ちている、架空の実績がある |
| 代替案と限界 | 読者の重要な反論に答え、結論が変わる条件を説明している | 有利な比較だけ、または限界を理由に判断を放棄している |
| 読みやすさ | 段落が前の問いを受けて進み、必要な用語と因果が理解できる | 短文を並べただけ、未定義の抽象語、つながらない追記がある |
| 日英の対応 | 問い、比較、数値、出典、確信度、限界、含意が一致する | 英語が要約になっている、または片方だけ内容や強さが違う |
| 記事固有の役割 | 関連記事との違いが明確で、タイトルと要約が本文の内容を表す | 複数記事が同じ問いと結論へ収束し、タイトルだけが違う |
| 引用とメタデータ | 本文と`publishedSources`、日付、日英のタイトルや説明が整合する | 本文だけの出典、対象時点の混同、本文と異なる検索用説明がある |
| 生成と表示 | ビルドと検証が成功し、日英のPC幅とスマートフォン幅で本文と図表を読める | 生成エラー、欠落、横にはみ出す図表、読めないリンクや文字がある |

技術確認では`pnpm build`を実行する。
このコマンドは`pnpm validate`も実行するため、変更後に独立した検証が必要な場合だけ追加で実行する。
`git diff --check`と変更範囲の確認を行い、無関係な作業を混ぜない。
ビルドの成功と文章の合格は、それぞれ確認する。

公開した場合は、配信成功、HTTP応答、公開本文と改稿版の対応、日英リンクと主要メタデータまで確認する。
公開確認を記事の事実検証や、Googleへの登録の代わりにはしない。

調査しても不明な事実は、適切に限定して記事の判断を維持できるかを検討する。
中心の判断を支えられない場合は、追加調査または論証の再設計へ戻し、薄い資料紹介として完了扱いにしない。
読者がこの記事で決められない事項は、その理由を本文に残す。

## 全体の完了と公開後の観測

全体の改稿完了は、対象36記事の日英72本文が共通条件を満たし、メタデータと表示の確認結果が台帳に残っている状態とする。
保留や未確認の項目が残る場合は、その記事を完了件数に含めず、残る理由を明示する。
最終確認では記事群を横断して、テーマごとの役割、似たタイトル、重複する説明、日英の対応、関連記事への案内を再点検する。

公開後の検索は、次の順に観測する。

1. 改稿した版が公開されているか。
2. GoogleがURLを認識し、その版の公開後に取得したか。
3. インデックスへ登録されたか。
4. 検索表示が発生し、どの疑問で来た読者かを確認できるか。
5. 実クエリと本文の問いが合い、関連記事へ進む必要を満たしているか。

取得されていない改稿版を、内容を改善しても評価されなかった版として扱わない。
再クロール後も未登録が続く場合は、取得内容、canonical、記事固有の付加価値、サイト内の役割を調べ直す。
登録や検索順位の変化だけで、改稿との因果効果を確定しない。

PV、流入元、関連記事への遷移、再訪、読了の代理指標は、対象サイトの計測を整えた後の観測項目とする。
計測前のアクセスを後から算出できるとは考えず、スクロールの深さだけで満足度を推定しない。
読者へ確認できる場合は、読後に判断がどう変わったか、理解できなかった点は何かを聞く。
編集者による通読と、実際の読者による評価は区別して記録する。
