Agent開発ツールで減る実装と、製品側に残る設計

AgentKit、Microsoft Agent Framework、Claude Agent SDKは、画面、手順定義、実行、評価をそれぞれ異なる範囲で提供する。顧客対応の想定例を通じ、道具が減らす実装と、顧客同定・権限・業務規則として製品側に残る設計を分ける。

比較の起点

Agent開発ツールは、どの実装を減らし、どの設計を残すのか

エージェントを製品に組み込むには、モデルを呼ぶコードだけでなく、利用者が操作する画面、外部データとの接続、途中経過の扱い、評価、障害時の表示が要る。2025年10月に公開されたAgentKit、Microsoft Agent Framework、Claude Agent SDKは、これらを同じ形では提供しない。既成の画面と視覚的な手順定義を含めるもの、SDKと実行環境を中心にするもの、コードから反復を組み込むものがある。

本稿の結論は、道具が減らす実装量だけを比べても選定できない、ということだ。既存アプリに何があり、誰を利用者と認め、どのデータを参照でき、どの操作で人の承認を求めるかによって、残る作業が変わる。製品名や機能数ではなく、「どの境界を提供側へ任せ、どの境界を製品側に残すか」で三つの発表を読む。

提供範囲

画面・手順定義・実行ループは、別々の形で提供される

OpenAIのAgentKit発表は、視覚的な手順定義と版管理のためのAgent Builder、接続を管理するConnector Registry、製品へ埋め込むチャット画面のChatKit、データセットとトレース評価を含むEvals機能をまとめて示した。公開時の提供状態は一律ではなく、ChatKitと新しいEvals機能は一般提供、Agent Builderはベータ、Connector Registryは対象を限ったベータだった。ここで減らせるのは、手順を描く画面、埋め込みチャット、評価を始めるための基盤の一部である。

Microsoft Agent Frameworkの発表は、オープンソースのSDKと実行環境として、道具との接続、決められた手順とモデル主導のオーケストレーション、可観測性、人による承認を説明する。これは、既存アプリへ実行を埋め込み、処理経路をコードやワークフローとして制御したい場合の部品に当たる。発表中のMicrosoft 365や共有実行環境との統合には将来計画も含まれており、公開済みの機能と同一視しない。

Claude Agent SDKの発表は、文脈を集め、行動し、検証して繰り返す実行ループ、ファイルとコマンド、サブエージェント、長い処理での文脈圧縮を説明する。既成の業務画面を提供するというより、アプリが必要な道具と規則を渡して反復を組み込むための部品である。三者の機能範囲は重なる部分があっても、同じ製品種別ではない。

道具が担える部分

手順の下書きと版管理、接続設定、チャット画面、反復実行、途中経過の観測、評価を始める枠組みである。どの範囲までを一つの製品が担うかは、発表ごとに異なる。

製品側に残る部分

顧客を識別する根拠、役割ごとのデータ権限、返金などの業務規則、既存画面での説明、保存先の契約、失敗時の責任者は、利用する製品に合わせてアプリ側が決める。

想定例

顧客対応では、下書きを作る処理と返金を認める処理を分ける

ここからは本稿の想定例である。既存のサポート画面に、返品遅延への問い合わせから返信案を作るエージェントを追加する。画面に入力された顧客IDとログイン中の担当者を、既存の認証基盤で照合する。次にエージェントは、許可された範囲の注文、配送、過去の対応記録を取得し、返品規約と照らした返信案を作る。資料を取得できない場合や顧客IDが一致しない場合は、推測した下書きを保存せず、担当者へ引き継ぐ。

Agent Builderを使う場合、問い合わせ分類、資料取得、下書き作成、確認依頼という経路を視覚的に定義し、試行結果を評価へ回せる。ChatKitを使う場合、対話画面を埋め込む作業を短くできる。しかし、どの既存アカウントを顧客として扱うか、返金可能な金額と条件をどの規約から読むか、下書きと確定済み回答を画面上でどう区別するかは、これらの部品の外に残る。

Microsoft Agent FrameworkやClaude Agent SDKを既存のバックエンドへ組み込む場合も同じである。前者のワークフローや人の承認機能、後者の反復と検証の仕組みは、照会と下書きの流れを構成する助けになる。だが、返金を実行する道具をいつ許可し、誰の承認を待ち、失敗や重複処理をどの記録で調べるかは、業務の責任境界として別に設計する必要がある。この例は製品の既定動作や導入実績ではない。

評価の位置

試作の速さと、完成した製品の品質確認を混同しない

AgentKitの発表には、短時間で手順を作った企業の紹介がある。これは視覚的な手順定義や既成コンポーネントが、試作の一部を短縮し得る例である。その所要時間を、別の組織が顧客データ、規約、監査、既存画面まで統合して公開する時間として読むことはできない。

上の顧客対応例なら、評価は少なくとも三つに分かれる。問い合わせに合う資料を取得したか、規約に沿った下書きになったか、権限外の顧客情報や未承認の返金操作を出さなかったかである。AgentKitのトレース評価、Agent Frameworkの可観測性、Claude Agent SDKでの検証ループは、それぞれこの確認を実装する材料になる。どれを使っても、受け入れ条件と失敗時の停止条件を自社のデータ契約から定義しなければ、評価の意味は定まらない。

選定の基準

残る設計は、道具の不足ではなく業務固有の責任である

既存アプリに顧客画面、認証、権限判定、監査記録があるなら、必要なのは新しいチャット画面より、そこへ実行ループを安全に接続する部品かもしれない。まだ利用者画面も評価の仕組みもない試作では、手順定義、埋め込み画面、評価をまとめて扱える道具が有効な場合がある。この違いは優劣ではなく、どの部分が未実装かによる。

開発道具を選ぶ前に、提供される画面、接続、実行、観測、評価を一つずつ書き出し、製品側に残す顧客同定、権限、業務規則、保存、承認と対応させたい。道具が複雑な実装を減らしても、製品の正しさを引き受ける境界までは引き受けない。この対応関係を明らかにすることが、発表の機能一覧を実際の開発判断へ変える。
