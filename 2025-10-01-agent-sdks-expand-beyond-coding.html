Agent SDKを汎用ワークフローへ組み込むとき、業務定義はどこに置くか

Claude Agent SDKは、文脈収集、行動、検証を反復する実行ループをアプリに組み込める。Looker MCPは定義済みの指標へ接続する。月次報告の想定例を通じ、実行制御と業務上の正しさ・承認が別の責任である理由を整理する。

問い

Agent SDKが汎用ワークフローに入るとは、何を再利用できるということか

Claude Agent SDKの発表は、Claude Codeで使われる仕組みを、調査、資料作成、顧客対応などのエージェントにも使える部品として説明する。中心にあるのは、文脈を集め、道具を使って行動し、結果を確かめて次の行動を選ぶ反復である。名称や用途例が広がったこと自体は、これらの業務で広く採用されたことや、正しい成果が自動で得られることを示さない。

本稿でいう「汎用ワークフローへ組み込む」とは、コード生成だけの補助から、実行ループと道具への接続をアプリに再利用できる部品へ役割が広がることを指す。ただし、何を売上と呼ぶか、誰がデータを見られるか、いつ外部へ確定結果を出すかは、その部品だけでは決まらない。月次報告を例に、実行を制御する責任と、業務上正しいと認める責任を分けて考える。

確認できる機能

Claude Agent SDKが提供するのは、仕事を進める反復の骨組みである

Anthropicの説明では、SDKのエージェントは「文脈を集める → 行動する → 作業を検証する → 繰り返す」という流れで動く。ファイルの検索と編集、コマンド実行、外部道具の呼び出しを組み合わせられ、サブエージェントは並列作業と文脈の分離に使える。長い処理では、要約によって文脈を圧縮する機能も説明されている。

これは、ある入力に対して一度だけ回答を返す仕組みより、途中の観測に応じて処理を変える仕事をアプリへ埋め込みやすくする。一方で、SDKが集計対象月、返品を控除した売上という定義、利用者の役割、最終報告の承認者まで与えるわけではない。前者は公開資料に記された機能範囲であり、後者は業務を実装する側が決める規則である。

SDKがアプリへ渡す制御点

文脈の収集、道具の呼び出し、反復、サブエージェントへの分担、結果の確認を組み合わせるための部品である。アプリは、各段階で何を入力し、どの道具を許可するかを実装する。

アプリと組織に残る業務規則

どのデータ定義を使うか、権限外の値をどう扱うか、矛盾した結果で停止する条件、確定前に誰が確認するかは、SDKの用途例からは決まらない。

データ定義との接続

計算を実行できることと、売上の意味を決めることは別である

Looker MCP Serverの発表は、AIアプリケーションがLookerのセマンティックレイヤーに接続し、あらかじめ定義された指標とアクセス制御を参照する構成を説明する。AIがSQLを即興で書くのではなく、Lookerへ問い合わせ、Looker側がSQLを生成するという範囲である。つまり、この接続は「売上」という言葉に既存の定義を結び付ける経路を与える。

それでも、接続が質問の解釈を正しくするわけではない。例えば「今月の売上」という依頼に対し、返品控除後の認定売上、受注額、請求額のどれを採るかは、組織が定めた指標と依頼の目的を照合して決める必要がある。選んだ指標、対象期間、絞り込み条件が依頼に合うかを確認する仕事は、道具を呼び出す仕事とは別に残る。

同じくGoogleのFirestore向けMCP Toolboxの発表は、エージェントがデータを照会・更新し、セキュリティ規則を検査する道具を示す。記事中の小売アプリの例はベンダーが説明のために置いた想定例であり、導入実績ではない。この例が具体化するのは、道具への接続が読み取りだけで終わらず、更新と規則検査まで及び得ること、そして実行権限と確定判断を分けて設計する必要である。

想定例

月次報告では、値と定義版と承認を同じ成果物に残す

ここからは、本稿の設計例である。経理チームが「9月の国内売上を報告してほしい」と依頼する。アプリはClaude Agent SDKの反復を使い、依頼から対象期間と地域を取り出し、Looker MCPを通じて候補となる指標を取得する。この段階で出力に含めるのは金額だけではない。使った指標名、参照した定義版、期間、地域フィルター、取得時刻を併せて記録する。

次に、アプリが定義版の更新日や承認済みの報告ルールと照合する。依頼が古い定義を前提としている、または質問と指標の意味が一致しない場合は、金額を確定値として配布せず、相違と不足情報を示して止める。条件を満たしたときだけ、指定された確認者へ下書きを渡し、確認者が承認して初めて外部向けの報告にする。この停止と承認は両製品の既定動作ではなく、実行ループを業務へ組み込む側が定める制御である。

この記録があれば、後から数値に疑義が出たとき、モデルの文面ではなく、どの定義、入力、絞り込み、確認を経たかを調べられる。SDKの再利用価値は、用途名を増やすことではなく、このように取得、計算、確認を一つの実行経路として組み立てられる点にある。

境界を残す

SDKは実行を広げるが、業務の正しさをアプリから取り去らない

同日に公開されたMicrosoft Agent Frameworkの発表も、SDKと実行環境を一体として説明し、接続、オーケストレーション、可観測性、人の承認を製品機能に含める。これは、SDKという語が小さなコード補助ライブラリだけを指さなくなっている一例である。ただし、この製品の機能一覧から、すべてのSDKが同じ制御を備えることや、採用が一般化したことは導けない。

SDKを選ぶときは「コーディング以外に使えるか」という用途の数ではなく、実行ループのどこを再利用し、業務定義、認可、記録、承認をどこへ置くかを確認したい。実行を汎用部品にしても、成果物を業務上正しいと認める根拠と責任者はアプリの外へ消えない。この分担を先に設計できる場合に限り、SDKはコード生成を越えたワークフローの実行部品になる。
