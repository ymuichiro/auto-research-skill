複数エージェントの設計は、どう運用モデルになるのか

Azure AI Foundry、Responses API、Semantic Kernelの資料を基に、依存関係、受け渡す根拠、検証、終了条件を持つ複数エージェントの仕事設計を考える。

AI Agents 2025年6月1日 最終更新 2026年9月20日
AI AgentRoundupOrchestrationEvaluation

問い

複数エージェントを、なぜ役割の図ではなく運用モデルとして設計するのか

担当を増やすだけでは協調にならない。前工程への依存、handoff で渡す入力と根拠、統合して検証する担当、終了または人へ戻す条件が必要になる。2025年5月の Azure AI Foundry Agent Service、Responses API、Semantic Kernel の orchestration は、こうした部品を実装や運用の対象として扱った。本稿では「運用モデル」を、役割名ではなく、仕事を再現・監査・停止できるようにする設計と呼ぶ。

依存関係

何が揃うまで次へ進めないか。並列にできる工程と、前の根拠を待つ工程を分ける。

handoff

要約だけでなく、入力、出典、未解決点、許可範囲を次の担当へ渡す。

統合と終了

誰が矛盾を検査し、何を完了、差し戻し、人への引き継ぎとするかを決める。

公開資料が示す範囲

協調機能は、役割分担を可能にするが、正しい運用を保証しない

Azure AI Foundry の一般提供と developer 向け資料、OpenAI の Responses API 更新、Semantic Kernel の orchestration は、エージェント、道具、実行履歴、複数担当の流れを構成する機能を示した。Google の multi-system agents と A2A は、他システムの担当へ仕事を渡す設計を扱う。これらは、組織固有の役割、権限、品質基準がすでに定義済みであることを意味しない。

Magentic-One や tau-bench は、複数の道具・担当・利用者とのやり取りを含む仕事で、結果だけでなく途中経路が問題になることを示す。ベンチマークを自社の性能へ転用せず、依存、状態、利用者との交渉を含む評価が必要だという設計上の示唆として扱う。

想定例

調査報告を作るなら、収集・執筆・確認の間に何を渡すかを決める

以下は設計例である。収集担当は一次資料の URL、公開日、該当箇所、未確認点を返す。執筆担当はそれを根拠に下書きを作り、確認担当は主張と出典の対応、古い資料、推測表現を検査する。資料収集は並列化できるが、結論の作成は根拠がそろうまで待つ。確認で根拠が不足すれば、終了ではなく収集担当へ差し戻す。

この流れでは、短い要約を渡すだけでは不足する。出典、引用可能な事実、執筆者の解釈、未解決条件を区別して渡す。統合役は矛盾を選び直し、公開前に人が最終判断する。単一の担当で十分な小さな報告では、handoff のコストが利益を上回るため、分割しない方がよい。

結論

複数エージェントの価値は worker 数ではなく、仕事を止めて検査できることにある

複数担当の設計を運用モデルにするとは、どの工程を並列化するかより、依存、handoff、統合、終了条件を記録できるようにすることだ。基盤はその実装を助ける。品質、権限、承認、例外時の責任は利用側が定める。まず単一担当の基準を作り、分割で時間、誤り、監督が改善する工程だけを増やすことが現実的な出発点になる。
