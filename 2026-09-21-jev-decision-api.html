LLMはすべてのif文を置き換えるのか。Jevが切り出す「判断API」

Jevは、閉じた選択肢と確率を返すTypeSafe AIの判断モデルである。BERT、生成LLM、Structured Outputsとの違いを整理し、曖昧な判断を安全にソフトウェアへ組み込む条件を考える。

文章を書かせたいわけではないのに、なぜLLMを呼ぶのか

「この問い合わせは返金依頼か」。「この契約に自動更新条項はあるか」。「この取引を人の審査へ回すべきか」。

どれも、業務ソフトウェアにはありふれた問いである。

必要なのは説明文でも企画書でもなく、次の処理を分岐させる判断だ。

それでも実装では、汎用の生成LLMに質問を渡し、文章かJSONを返させ、その値を読んで処理を決めることが多い。

この使い方が常に過剰とは限らない。

問い合わせの理由を説明し、必要な追加情報を尋ね、例外を処理するなら、生成モデルの柔軟さが必要になる。

しかし、閉じた候補から選ぶだけの場面では、「文章を書いてほしいわけではないのに、なぜ文章生成モデルを使うのか」という問いが残る。

TypeSafe AIが2026年9月15日に早期公開したJevは、この問いを製品の出発点にした。TypeSafe AIの発表によれば、Jevは入力された状態と型付きの質問を受け、文章ではなく、選択肢、尺度、または真偽に対応する構造化された回答と確率を返す。

本稿では、この製品が提示する層を判断APIと呼ぶ。

これは確立した業界分類ではない。

生成、計算、実行を担うモデルとは別に、自然言語を読んだうえで、アプリケーションがあらかじめ定めた候補から判断を返す部品を指す、本稿の整理である。

現場では、学習済み分類器と汎用LLMの間が空いていた

従来の選択肢をBERTとLLMだけに還元すると、歴史を単純化しすぎる。

ゼロショット分類は以前から研究されており、ラベル付きのタスク別データを見ずに分類する設定も2019年には体系的に評価されている。Yinらの論文

それでも実務の設計は、しばしば二つの作業様式の間で選ばれてきた。

学習済み分類器

対象ラベルを決め、データを集め、ラベル付けし、評価してから配備する。BERTは事前学習済み表現にタスク固有の出力層を加えて微調整できる設計を示した。BERT論文

汎用の生成LLM

新しい問いにも、その場の指示で答えられる。生成、説明、複数の条件をまたぐ推論まで一回の呼び出しに含められる一方、判断だけでも生成モデルの呼び出しになる。

Jevの判断API

状態と閉じた質問を渡し、候補、尺度、真偽と確率を返す。モデルの自由度を、アプリケーション側が定めた判断空間へ絞る。

この図は性能の序列ではない。

手書きの規則で決まる条件、文章や説明が必要な仕事、訓練済みモデルが十分に高精度な領域は、それぞれ残る。

Jevの着眼点は、両端のどちらが賢いかではなく、自然言語を読む必要はあるが、開いた文章を返す必要はない分岐を、独立した呼び出しとして扱ったことにある。

Jevは、閉じた判断を三つの型で受け取る

JevのHTTP APIは、アプリケーションの状態と質問の対応表を受け取り、各質問に一つの回答を返す。API仕様

質問の識別子はアプリケーションが決め、モデルに渡るのは質問文、選択肢、判定基準である。

Choice

定義した候補から一つを選ぶ。問い合わせ先を返金、技術、営業のどこへ送るかのような判断に使い、各候補の確率と信頼度も返す。Choiceの仕様

Score

あらかじめ説明した順序尺度上で状態を評価する。重大度や緊急度のように、候補間に順序がある判断へ向く。Scoreの仕様

Noul

真偽を問い、真である確率を0から1で返す。返金要求が含まれるかのような二値の判断に使う。Noulの仕様

分類器らしく見えるのは、ここだけを見れば当然である。

ただし、回答候補と評価基準は呼び出し時にアプリケーションが渡せる。

今日の分類をrefund / support / salesとして定義し、明日はabuseを追加する変更は、再学習の開始ではなく、質問と評価ケースを更新する変更になる。

この可変性が、Jevを固定の分類モデルではなく、分類器を作る行為の一部をAPIへ移した製品として見せる。

Structured Outputsと競合するのは、出力形式ではない

「安価なLLMにStructured OutputsでJSONを返させればよい」という反論は正しい。

OpenAIのStructured Outputsは、開発者が渡したJSON Schemaにモデル出力を適合させる機能であり、型が崩れた出力を受け取らないという目的には有力である。OpenAIの発表

したがって、形式だけを理由にJevを選ぶことはできない。

Schemaに従うJSONと、事実に即した正しい判断は別の性質だからだ。

この二つの経路は、次のように分けて考えるとよい。

生成LLMとStructured Outputs

汎用モデルを、決めた構造の回答器として使う。説明、例外処理、抽出、推論も必要なら、一つのモデル呼び出しに含められる。

Jev

閉じた判断を最初からAPI契約にし、各候補の確率と信頼度を返す。文章の説明を返す用途には使えない。

TypeSafeは、出力を逐次的に生成するLLMと対比し、Jevでは複数の質問を同じ状態に対して並列に評価すると説明する。Introduction

同社のワークフロー評価も、分解した質問とコードによる制御を前提にしている。Workflow evals

ただし、これはベンダー自身が作ったハーネスと、外部モデルの合議ラベルを基準にした評価である。

同社もハーネス設計者による偏りの可能性を記しているため、速度や費用の主張を、独立した精度比較の結論として扱うことはできない。

Jevが「より賢い」から選ばれるとは限らない。

生成の自由度を捨て、候補と確率をソフトウェアの一級の入力にしたいときに、設計上の適合が生まれる。

学習は不要になっても、判断の設計と評価は消えない

Jevを「学習なしで使える分類器」と呼ぶことには、説明としての強さがある。

タスクごとの重み更新を、利用企業が最初から行わずに済むからだ。

しかし、「要件を書いてAPIを呼べば分類が完成する」と読むと誤る。

分類の責任が消えるのではなく、ラベル、判定基準、閾値、例外の設計としてアプリケーション側へ移る。

微調整分類器の変更

要件をラベル定義へ変え、データを収集してラベル付けし、訓練と評価を経てモデルを配備する。新しいラベルは、この機械学習の流れを更新する契機になる。

判断APIの変更

要件を質問と判定基準へ変え、通常例と境界例の評価セットを作り、行動の閾値と人への引き渡し条件を定める。新しいラベルは、質問、評価、分岐規則を更新する契機になる。

後者は、機械学習の運用を不要にするとは言えない。

少なくとも、判断ごとに固有の訓練データを集めて再学習する工程を、初期導入の必須条件から外せる可能性がある。

その代わり、誰がabuseに含まれる事例を定義し、どの誤分類を許容せず、どの回答を人に渡すかを、ソースコードと評価記録で追えるようにしなければならない。

確率の扱いも自動化の許可証ではない。

ニューラルネットワークの確率は校正されていないことがあり、校正は個々の回答の正しさを保証する性質ではない。Guoらの研究

TypeSafeのドキュメントも、校正は予測の集合に対する性質であり、個別の回答を保証しないと説明する。System Oneの仕様

確率はif文を置き換えるのではなく、if文へ入力する

判断APIを業務へ組み込むとき、モデルの出力を直接、外部操作に結び付けるべきではない。

返金、本人確認、送金、公開のように誤りのコストが異なる操作では、必要な証拠と行動条件も異なる。

たとえば問い合わせを振り分ける想定例では、モデルは担当候補を出し、プログラムが必須項目、信頼度、操作権限を順番に確かめる。

if missing_required_record(ticket):
    route_to_human(ticket)
elif decision.confidence < ROUTING_THRESHOLD:
    route_to_human(ticket)
elif decision.choice == "refund":
    open_refund_review(ticket)
else:
    route_to_support_queue(ticket, decision.choice)

これは実在する導入例ではなく、判断と行動の責任を分けるための想定例である。

モデルは問い合わせを読む。

プログラムは、何を自動処理でき、何を確認へ戻すかを決める。

TypeSafeも、問い合わせを決定的な処理、専門LLM、人の担当者へ振り分ける設計を例示し、低い信頼度や高い複雑さを人へ戻している。Intent routingの仕様

高リスク操作には、正解らしい分類よりも、誤ったときに停止できる分岐、操作前の決定的な照合、監査できる記録が必要になる。

この分担があるとき、AIはアプリケーションの中心で自由に振る舞うエージェントではなく、プログラムの途中で何度も呼ばれる「曖昧なif文」になる。

Jevを試すなら、正答率より先に止まる条件を決める

Jevの型安全性は、意味の安全性を保証しない。

Jev 1.13の公開ドキュメントには、数値計算、日時比較、複数段の間接的な問い、不要な情報を含む長い入力、敵対的な内容が失敗要因として記載されている。文章生成も用途外である。Jev 1.13の既知の限界

このため導入の比較対象は、Jevだけではない。

手書き規則、既存の微調整分類器、Structured Outputsを使う汎用LLM、人の確認を含め、同じ評価セットで比べる必要がある。

  • 通常例だけでなく、対象外、矛盾、曖昧、攻撃的な入力を評価セットに入れる。
  • 判断の種類ごとに、誤って通すことと、人へ回しすぎることの費用を分けて測る。
  • 高信頼度の回答でも抽出監査し、誤りが見つかれば質問、判定基準、閾値、または規則を更新する。
  • モデル更新で回答が変わるため、閾値を調整した運用ではバージョンを固定し、変更時に再評価する。Modelsの仕様

選択的分類の研究は、誤りのリスクと自動判定の対象範囲を交換する考え方を扱ってきた。GeifmanとEl-Yanivの論文

Jevの確率と信頼度は、この交換を実装しやすくする入力にはなり得る。

ただし、適切な閾値と対象範囲は、製品が一律に決められるものではない。

残るのはJevそのものではなく、判断を部品にする需要かもしれない

Jevが長期に勝つかどうかは、まだ判断できない。

早期公開直後のベンダー評価は、汎用LLM、既存の分類器、業務データを横断した独立比較ではない。

一方で、生成LLMのSchema準拠、ゼロショット分類、信頼度に基づく棄却は、すでに別々の技術として存在していた。

Jevはそれらを「状態を読み、閉じた判断と確率を返し、コードが行動を決める」という一つの製品契約にまとめた。

この契約が定着すれば、AIは会話画面や自律エージェントだけでなく、問い合わせの振り分け、文書の判定、危険度の見積もり、確認への差し戻しという小さな分岐へ入っていく。

Jevの注目点は、モデルの万能さではない。

「生成AIほど重くなく、固定の分類器ほど変更しにくくない」中間の仕事に、判断APIという設計上の居場所を与えたことにある。
