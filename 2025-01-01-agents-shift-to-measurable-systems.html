AIエージェントの比較は、なぜ測定可能な仕事の設計へ向かったのか

ReAct、Toolformer、WebArena、SWE-bench、OSWorldを比較し、AIエージェントを「道具を呼べるか」ではなく、環境内の仕事をどの条件で終えられるかで評価する理由を整理する。

AI Agents 2025年1月1日 最終更新 2026年9月20日
AI AgentRoundupBenchmarkTool Use

問い

AIエージェントは、なぜ「道具を使える」だけでは比較できないのか

2025年1月1日までに公開された研究を読むと、AIエージェントの評価対象は、単発の応答や API 呼び出しだけでは収まらなくなっていた。ReAct と Toolformer は外部情報や API を行動に組み込む方法を扱い、WebArena、SWE-bench、OSWorld は、環境の中で仕事を最後まで終えたかを測った。本稿の結論は、これらの資料が「市場全体が移行した」と証明するというものではない。ツール、環境、完了条件を結び付けて測るための部品が、比較可能な形でそろってきた、という設計上の観察である。

行動を選ぶ

必要な情報を取りに行くか、どの API にどの引数を渡すかを決める。

環境を変える

画面、リポジトリ、データの状態を読み、複数の操作を順に実行する。

終わったことを確かめる

最終状態、根拠、許可されない副作用を、仕事ごとの条件で判定する。

行動の設計

ReAct と Toolformer は、同じ「ツール利用」を別の角度から扱った

ReAct は、推論の記述と task-specific action を交互に生成し、観測を次の判断へ使う枠組みを示した。質問応答の例では、Wikipedia の検索、ページ内検索、回答の確定という操作が連なる。ここで確認できるのは、モデルが途中で外部情報を取り込めることと、その過程を人が読める軌跡として残せることである。論文が扱うのは特定のベンチマーク上の比較であり、外部検索を足せばあらゆる問いへの回答が改善するとまでは言えない。

Toolformer は、どの API をいつ呼ぶか、どの引数を渡すか、戻り値を後続の生成へどう取り込むかを自己教師ありで学ぶ方法を提案した。計算機、質問応答、検索、翻訳、カレンダーが対象に含まれる。これは ReAct の実装手順を置き換える資料ではない。前者が推論と観測の往復を、後者が API 呼び出しを学習へ取り込む問題を扱うため、両者を同じ成功指標へ縮約しない方がよい。

ここで確認できる事実

ツール呼び出しの設計には、選択、引数、観測の利用という別々の問題がある。呼び出しが成功した事実は、後続の仕事が完了した証拠ではない。

完了条件

環境ベンチマークは、回答ではなく最終状態を採点対象にした

WebArena は、電子商取引、フォーラム、共同ソフトウェア開発、コンテンツ管理の機能する Web 環境で、長い操作列の機能的な完了を測る。2024年4月の版で論文が報告した比較では、GPT-4 を基にした最良のエージェントは end-to-end task success 14.41%、人は 78.24% だった。この数値は WebArena の環境、タスク、当時のベースラインに限られる。自社サイトの自動化成功率や、現在のモデルの性能として転用してはならない。

SWE-bench は、12 の Python リポジトリにまたがる 2,294 件の実際の GitHub issue と対応する pull request から、コードベースと issue 説明を渡し、修正を行わせる。ここでの仕事はコード片を提案することではなく、問題を読み、関係するファイルを変更し、テストで最終状態を確かめることに近い。OSWorld は、Ubuntu、Windows、macOS を含む実コンピュータ環境に 369 のタスクを置き、初期状態の設定と実行ベースの評価スクリプトを用意した。論文での最良モデルの 12.24% と人の 72.36% という比較も、GUI の位置合わせや操作知識を含む、その環境固有の測定である。

BrowserGym の公開版は、複数の Web エージェントベンチマークを共通の観測・行動空間で扱い、実験管理をそろえることを目指した。これらの研究が共通して示すのは、エージェントの働きを見るには、入力文だけでなく、初期状態、許可された操作、完了の判定器を明示する必要がある、という点である。

製品面

公式の構築機能は、測定そのものではなく、仕事境界を実装する部品を提供した

2024年の Amazon Bedrock Agents の更新は、action group、構成の簡略化、アプリケーションへの制御返却、Infrastructure as Code を含んだ。Vertex AI Agent Builder や、Claude の tool use も、知識ソースや外部機能と接続するアプリケーションを構成する選択肢を示した。これらは、利用者の仕事が正しく終わることをベンダー資料だけで保証するものではない。

ただし、構成要素が製品面に現れたことで、評価する仕事境界を実装に落とし込みやすくなった。たとえば、どの API を許すか、結果をアプリへ戻す場所はどこか、どの情報源を参照するかを、モデルへの指示だけでなく構成として置ける。Building effective agents が区別する workflow と agent という設計上の分類も、万能な自律性を前提にせず、仕事に合わせて制御の強さを選ぶための参考になる。

具体化

「社内資料から保守期限を答える」仕事なら、採点表を先に作る

以下は研究成果を実務へ読み替えるための想定例である。利用者が「この機器の保守期限を教えて」と尋ね、エージェントが社内文書検索を使うとする。検索 API が応答しただけでは足りない。旧型機種の資料を返していれば、操作は成功していても根拠は誤っている。型番や契約によって期限が変わるなら、もっともらしい日付を生成することも完了ではない。

入力と許可操作

機器の型番、契約識別子、検索可能な文書リポジトリを定める。外部送信や契約変更はこの仕事に含めない。

完了の根拠

適用できる文書の版、期限を記す箇所、契約との対応を回答に添える。根拠不足なら「不明」と返すことも正しい結果に含める。

比較する記録

同じ問い合わせ群に対し、条件を満たした回答、根拠の取り違え、時間、呼び出し回数を記録する。単純な API 成功率とは別に集計する。

この採点表は特定の研究のスコアを自社へ持ち込むものではない。WebArena などが行うように、仕事の初期状態と最終状態を自分たちの条件で明文化するための設計例である。

設計上の結論

測定可能な仕事は、デモを小さくするためではなく、失敗を読めるようにするために必要だ

2025年初頭の研究と製品資料から得られるもっとも実用的な示唆は、エージェントを「できることの一覧」で比較しないことだ。道具の選択、環境内の操作、最終状態の三つを分けると、検索が誤った資料を選んだのか、操作が途中で止まったのか、採点条件が曖昧なのかを区別できる。本稿では、この区別を測定可能なシステム設計と呼ぶ。

一方で、ベンチマークの成功率や製品の提供機能を、そのまま自組織の業務成果へ一般化することはできない。最初に扱う仕事は、参照範囲と最終状態を定義しやすく、外部副作用が小さいものに絞る。その上で、失敗の記録を使って許可操作や採点条件を更新することが、派手なデモを運用可能な仕事へ変える手順になる。
