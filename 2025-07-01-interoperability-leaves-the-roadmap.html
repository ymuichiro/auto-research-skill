問い

相互運用は、何を交換できる状態を指すのか

2025年春から夏の A2A、MCP、OpenAPI をめぐる発表は、接続を試験できる対象を具体化した。A2A は他エージェントへ task、状態、artifact を渡す形を、MCP は道具やデータへ接続する形を、OpenAPI は操作を記述する形を扱う。これらがそろっても、相手を業務上そのまま置換できるとは限らない。本稿は、接続可能性と、出力の意味、認証範囲、失敗処理、承認責任まで一致する交換可能性を分ける。

接続で渡すもの

道具・resource、task・artifact・status、操作の入力と出力をやり取りする。

接続だけでは渡らないもの

誰の権限で呼ぶか、出力が何を意味するか、危険な変更を誰が承認するかは別に定める。

検査するもの

出力 schema、認可範囲、timeout、再試行、未確定状態の扱いを、交換前後で比べる。

公開資料の役割

A2A、MCP、マネージド基盤は、異なる接続面を扱う

A2A の発表と Linux Foundation への寄贈は、agent card、capability discovery、長い task の lifecycle をオープンな協調課題として扱った。Google Cloud の MCP database integrations は、開発者が道具とデータへ接続する具体例を示した。OpenAI の Responses API の remote MCP、Azure AI Foundry の A2A/MCP/OpenAPI 対応は、マネージド実行とオープンな接続方式を組み合わせる選択肢を示す。

これらの資料は、接続の形式や提供範囲を説明する。互換性のある業務結果、組織のセキュリティ要件への適合、あるいは複数製品の同等性能を証明する資料ではない。tau-bench のような道具・利用者・状態を含む評価は、インターフェースが同じでも仕事の最終状態を別途検査する必要を思い出させる。

想定例

検索担当を差し替える前に、出力と失敗の契約を比べる

以下は設計例である。A2A 経由で呼ぶ検索担当を別の提供者へ替える。task の送信と artifact の受信ができても、片方は引用 URL と文書版を返し、片方は本文だけを返すかもしれない。片方は利用者ごとの権限不足を返し、もう片方は空の結果として扱うかもしれない。利用者が「見つからない」と判断する条件も変わる。

交換テストでは、同じ入力に対し、出力 schema、根拠の有無、認証失敗、timeout、再試行、監査記録を比べる。外部送信やデータ更新が含まれるなら、どの段階で利用者・組織の承認を求めるかも変えてはならない。通信が通ることを合格にせず、仕事の完了条件が保たれるかを確認する。

結論

相互運用を設計前提にするとは、交換できない責任も先に書くことだ

公開仕様により、他のエージェントや道具へ接続することは以前より検査可能になった。本稿の結論は、相互運用が完成したというものではない。接続形式を共通化しても、認証、データの意味、失敗時の責任、承認規則はアプリケーションと組織の契約として残る。そこまで含めて比べることが、将来の差し替えを可能にする設計になる。
