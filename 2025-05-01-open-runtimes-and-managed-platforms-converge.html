オープンな接続、マネージド実行、承認設計をどう分けるか

OpenAI、AWS、Google、Microsoftの2025年春の資料を読み、プロトコルによる接続、ホストされた実行、利用者・組織の承認を別々の責任として組み合わせる設計を考える。

AI AgentRoundupInteroperabilityRuntimeApproval

問い

接続、実行、承認を一つの「エージェント機能」として扱うと何を見落とすか

2025年春の資料では、OpenAI の構築用部品、AWS の協調と人による確認、Google の multi-system agents と A2A、Microsoft の Semantic Kernel Agents が、異なる場所で公開された。これらは一つの完成した共通基盤を示すものではない。本稿では、プロトコルによる接続、マネージドな実行、変更を確定する承認を別々の責任として置く。三つを分けると、どの部分を交換でき、どの判断が組織に残るかを説明できる。

接続

タスク、道具、成果物を別システムへ渡す形式と認証範囲を定める。

実行

モデル、道具、状態、協調を使って仕事を進め、記録を残す。

承認

誰が変更を許すか、何を確認するか、例外をどこへ返すかを決める。

異なる責任

A2A とマネージド基盤は、同じ問題の別の層を扱う

Google の A2A 発表は、異なるエージェントがタスク、状態、成果物をやり取りするためのプロトコルを提示した。これは、接続先が同じ実行基盤で動くことや、相手の業務方針を引き受けることを意味しない。Google Cloud の multi-system agents、AWS の multi-agent collaboration、OpenAI の agent-building tools、Semantic Kernel Agents は、それぞれ実行や協調を構成する選択肢を提示した。提供範囲と公開状態は資料ごとに異なるため、同じ成熟度へ並べない。

AutoGen、Magentic-One、BrowserGym の研究は、複数担当や外部環境の仕事で、観測、状態、完了条件が必要なことを示す。プロトコルは相手を呼べる形にし、実行基盤は仕事を進める形にする。どちらも、顧客情報を送ってよいか、休暇申請を承認してよいかという組織の判断を代替しない。

承認の境界

Bedrock の確認と control return は、変更の責任を分けて扱う例になる

AWS の human-in-the-loop の例は、エージェントが action group を実行する前に利用者確認を求める構成と、アプリケーションへ制御を返す構成を説明した。確認は利用者がその操作を望むかを確かめる機構であり、組織の承認規則や外部システムの認可を自動的に満たすものではない。

休暇申請を考えると、HR API へ接続できること、従業員が申請内容を確認すること、上長の方針に従って承認されること、記録が実際に更新されたことは四つの別の状態になる。この区別があれば、接続障害、本人の取り消し、承認待ち、更新失敗を同じ「失敗」として扱わずに済む。

想定例

休暇申請を、接続・実行・承認・更新として順に追う

以下は設計例である。エージェントが残日数を照会し、申請案を作る。A2A や道具の契約は、どの担当または API に依頼するかを定める。マネージド実行は、その依頼、状態、応答を扱える。利用者確認は日付と理由を確かめる。上長承認は組織規則を適用する。最後に HR システムの記録を照合して初めて、更新を完了とする。

この流れで必要になるのは、各段階の入力、権限、結果、失敗時の戻り先である。接続方式を替えられても、承認規則や保存先の整合が自動的に移るわけではない。反対に、実行基盤を替えても、仕事の完了条件を変えずに比較できるようにしておくと、設計変更を検査しやすい。

結論

一つの設計図に置くべきなのは、製品名ではなく責任の境界である

春の発表群から読み取れるのは、接続、実行、協調、確認の部品が別々に選べるようになったことだ。本稿の解釈では、これらを同じ設計図に置く価値は、相互運用が完成したと主張することではない。接続契約、実行の記録、承認の責任を分け、どこに人と組織の判断を残すかを明示することにある。
