How external text can become an instruction to act

Imagine an email-summary agent executing a sentence in the email that asks it to send information to a website “for verification.” Content it was supposed to read has become a reason to use a tool. This is a hypothetical illustration of the mechanism, not a claim that every agent follows such instructions.

OpenAI's March 11 explanation treats prompt injection through external content as a problem resembling social engineering. Its defensive objective extends beyond identifying suspicious text to constraining where information can be sent even if the agent is influenced.

That distinction supports evaluating two separate outcomes before release: whether the agent recognizes an attack and whether the induced action can actually execute. Define which work may continue and which operations must stop according to the application's permitted scope.

Transmission checks, tool policies, and human approval act at different points

OpenAI describes Safe Url as detecting potential transmission of conversation information to third parties and either requesting confirmation with the relevant information or blocking it. This concerns information leaving the system, not correcting every mistaken inference. When confirmation is requested, users need to understand what will go where.

AgentCore Policy, announced generally available on March 3, controls a different point. Rules outside the agent's code evaluate tool access and inputs for calls passing through AgentCore Gateway. A model may select a call while the policy still refuses its execution.

The same rules do not automatically cover a separate API connection bypassing the Gateway. Blocking an email tool does not establish containment if another communication path can send the same information. Verify which actions pass through the check and which other paths remain in the actual deployment.

Anthropic's framework for safe agents discusses stopping or redirecting work and granting persistent permission for trusted routine actions. Human confirmation therefore need not occur at the same frequency for every operation. Specify pre-authorized actions and changes requiring individual review, then test that the configured distinction holds.

Release tests should verify permitted work and prohibited actions

For an email-summary workflow, first check that ordinary email can be summarized. Then place a request for external transmission in the message and inspect network and tool records as well as the response. This is a proposed test, not a measured comparison of the vendors' defenses.

  • Does permitted summarization complete without unnecessarily blocking safe work?
  • If an unrequested transmission is attempted, does it stop before the information leaves?
  • If review is requested, does rejection stop execution, and does approval permit only the displayed destination and content?

A written refusal does not prove that no transmission occurred. Conversely, the execution system's adherence to permissions can be measured separately from whether the agent explains the attack. Record the model, connections, and permission settings so the same tasks can be rerun after changes.

The results can support releasing a particular configuration, but cannot guarantee resistance to unknown attacks. Bound the information and actions available, then verify that legitimate work completes and prohibited operations stop within that scope. Make observed enforcement, rather than a count of safety features, part of the release decision.
