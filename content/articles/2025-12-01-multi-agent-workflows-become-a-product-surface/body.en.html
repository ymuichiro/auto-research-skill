Question

When a multi-agent path becomes visible, who can decide what?

A diagram that connects agent roles with arrows is not enough to review a multi-agent process. A reviewer needs to distinguish what a step receives, which condition selects a branch, which input reaches the next step, and where a failed run stops. Foundry Agent Service’s multi-agent workflows, announced as a public preview in November 2025, presented components for defining such paths in diagrams and YAML, tracing runs, and evaluating work.

The article’s argument is that making a workflow visible does not itself prove business correctness or authorization. A path definition, the record of a path actually taken, an evaluation of the result, and authorization for an external action are separate artifacts, even when they refer to one another. An account-request scenario separates the decisions each artifact supports.

Scope of the public preview

Diagrams and YAML define possible paths; run records show the path taken

Microsoft’s announcement describes synchronized visual editing and YAML definitions. A workflow is represented by nodes and connections, can store agent output in local variables for later steps, and supports structured JSON Schema output, Power Fx expressions for conditions and transformations, and immutable versions on every save. A diagram and its YAML definition let reviewers inspect which input may reach which step and which branches are intended.

A run record answers a different question. The announcement says a team can trace agent calls, inputs and outputs, variable assignments, and the branch path taken step by step. That can show whether a particular input followed the expected branch and at which value it stopped. The initial release’s observability, however, focuses on individual Foundry agents within the workflow. Displaying a path does not establish that every external system state can be traced.

The decision supported by a definition

It lets a team review intended steps, input and output shapes, branches, variables, and versions. A definition states that a path is possible; it is not evidence that the path was executed.

The decision supported by a run record

It lets a team investigate activated nodes, variable updates, branches, and stopping points for one input. A record alone does not establish that an input was factual or that an external action was appropriate.

Scenario

Treat definition, execution, evaluation, and approval as four artifacts in an account request

This is a scenario from this article. An employee requests a work account. The first step extracts a department, required roles, and an expiry date from the request into an agreed JSON form. The second step checks those values against a department directory and a role catalog, branching to a request for more information when data is missing or a combination is disallowed. The third sends an application including the check results to an administrator. Only after approval does a separate registration step create the account.

In this flow, the diagram or YAML is the first artifact. It fixes the path through extraction, checking, a request for more information, administrator review, and registration, along with the fields passed between steps. The second artifact is the run record for one request. It can show that a missing department name sent the run to the more-information branch and which role-catalog version was consulted. The third artifact is the evaluation result. Using the built-in evaluators named in the announcement or an evaluator created by the organization, the team can check whether department, role, and expiry date meet required forms and whether it allowed a combination that violates a rule.

The fourth artifact, approval, is a separate record of who allowed which role for whom and until when. A boolean produced by an agent or a schema-valid “approved” string is not an approval record. The organization must decide whether the original approval can be reused when a role or expiry date changes after approval. This is not a default Foundry request flow or a reported deployment. It illustrates how to separate use of the documented definition, trace, and evaluation components.

Evaluation and constraints

Type checks and evaluators do not replace approval

JSON Schema can make the shape of values exchanged between steps consistent. It can check that a department is a string, roles are an array, and an expiry date has a date format. A nonexistent department can still be a string, and a role combination can violate policy while satisfying its type. Built-in and custom evaluators are material for assessing quality, safety, and organization-specific rules; they do not automatically replace the decision of the organization’s authorized approver.

Trials should therefore include more than successful requests: an unknown department, a registration request before administrator approval, a request whose role changes after approval, and a run that fails while consulting an external directory. Check separately that the definition stops as expected, the run record makes the cause traceable, the evaluation identifies the violated rule, and the registration step does not run without an approval record.

Relation to adaptive planning

Changing the order of investigation does not remove fixed conditions

Magentic-One describes a research system in which an orchestrator tracks progress, replans to recover from errors, and assigns browser, file, and code work to specialized agents. It is a research example showing that a multi-agent system need not follow only a predetermined sequence. It is not a performance comparison with Foundry’s preview features or a claim that the implementations are the same.

A system may change the order in which it investigates missing information in an account request. The conditions that necessary checks and administrator approval must hold before registration do not change. Separating flexible investigation and follow-up work from approval, recordkeeping, and stop conditions that must remain is the prerequisite for connecting a visible workflow to business operations.
