Start with the recipient and the information being exchanged

On March 13, AWS announced AG-UI support in AgentCore Runtime, alongside its existing MCP and A2A support. The addition handles communication with user-facing applications, including streamed text, tool results, and processing updates. It is a concrete example of one runtime hosting all three protocols.

That does not mean installing all three automatically produces coordinated agents with correctly enforced human approval. This article compares three interactions: calling a tool, requesting work from another agent, and updating a user interface. These are useful design categories, not three mutually exclusive layers mandated by the specifications.

What each recipient receives in a refund workflow

MCP: connect to invoice data

The requesting agent searches invoice numbers or contract conditions. It exchanges search criteria and tool results, rather than a decision that a refund is permitted.

A2A: request an investigation

An invoice or policy specialist receives an investigation task, additional required input, progress, and an artifact. This represents the exchange where the recipient needs to be another agent.

AG-UI: update the user

The application receives that research is in progress, the amount found, and why confirmation is required. Being displayed does not mean that a refund was authorized.

The application: bind approval to execution

It verifies who approved which invoice, amount, and destination, and ties that approval to the refund API call. It also defines rejection, expiry, and a user leaving the screen.

This is a hypothetical use of the specifications, not a claim that a refund service needs all three connections. A small workflow may need only search and its existing interface.

MCP tool calls and A2A task exchanges

MCP's tool specification defines listing available tools, describing their arguments, invoking them, and returning results. An invoice-search tool, for example, accepts search criteria and returns matches. Its implementation could itself use AI, so the presence of an AI system on the other end does not distinguish MCP from A2A.

The A2A 0.3.0 specification describes capabilities through an Agent Card and exchanges task status and artifacts. Its states include input-required. Those interactions matter when a separate agent investigates an invoice, requests missing information during the work, and returns its findings.

A long-running operation does not by itself require A2A. The 2025-11-25 MCP specification also includes experimental tasks for tracking execution and retrieving results later. Compare whether a function call is sufficient, whether capability descriptions and ongoing dialogue are needed, and which versions and features both endpoints actually support.

Displaying progress does not authorize a refund

While a remote agent works, the user may not know what it is waiting for. AWS's AG-UI announcement describes streaming text and tool results, along with synchronizing information that can update progress indicators. This connection makes intermediate processing information available to the application interface.

Consider a hypothetical refund following an invoice investigation. Showing an amount and an approval button does not establish that the refund API cannot run before approval. The execution system must verify who approved which invoice and amount, then bind that approval to the actual call. Handling rejection or a closed window is also an application responsibility.

In this scenario, MCP could provide invoice access, A2A could carry the investigation request, and AG-UI could carry information to the interface. The protocol names do not determine refund permissions or approval conditions. MCP itself requires server-side access controls and does not mandate a particular user interface.

Adopt the connections needed and align their business meaning

Simply searching invoices and displaying them may not require delegating work to another agent; adding A2A would then have little purpose. If an existing interface and API communicate progress adequately, replacing them with AG-UI should also depend on a demonstrated benefit.

When connecting implementations, agree on what “investigation complete” means in addition to establishing communication. Distinguish a proposed refund, an approved refund, and an executed refund, and retain records that connect them to the same request. Shared message formats do not automatically align those business meanings.

The useful comparison is which exchanges each specification can support. Identify the recipient and information first, then adopt features missing from the existing implementation. That keeps the number of supported protocols separate from the work the system can actually finish.
