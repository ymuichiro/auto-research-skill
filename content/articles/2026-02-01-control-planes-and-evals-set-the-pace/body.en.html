The question before a change

Did fixing a new inquiry break an established refund or escalation behavior?

After revising its routing instructions, a support agent correctly handles complex questions about a new product but starts automatically answering return cases that it previously escalated to staff. This is a scenario from this article. Success on the repaired task does not establish that the behavior which had to remain survived.

This article asks what to compare and record before accepting a candidate change. Its conclusion is not a general rule that evaluation determines update speed. It is an operational observation: without a way to detect regressions, a team cannot safely judge the range affected by a change, so the range it can update becomes narrower.

The role of evaluation

Separate tests that improve capability from tests that protect established work

Anthropic’s guide to agent evaluations separates capability evaluation, which targets tasks an agent struggles with, from regression evaluation, which checks that work the agent used to handle has not deteriorated. The former looks for room to improve from a low pass rate; the latter preserves a near-complete pass rate and signals backsliding.

In support, correctly classifying a complex question about a new product can be a capability task. Established behavior—escalating an ambiguous return case, not calling a refund tool before identity verification, and stopping above an allowed refund amount—belongs in a regression suite. One average score can hide a dangerous automatic response or an incorrect tool call behind improved new-task classification.

The capability question

Can the candidate version route a previously difficult new-product inquiry using the necessary material? This task measures room for improvement.

The regression question

Does the candidate retain escalation, identity verification, refund conditions, and safe stopping behavior that the current version already kept? This task measures whether an established promise has been broken.

Comparison card

Run the candidate and current version against the same work, grading, and conditions

A comparison card records at least the version of the evaluation suite; the input and success condition for each task; graders and rubrics; model and instructions; tools and branch conditions; execution environment; and the candidate or current workflow definition. Anthropic distinguishes a task, trial, grader, transcript, outcome, and evaluation suite. Keeping those elements linked before reducing them to one score makes it possible to investigate what actually changed.

Suppose a candidate improves new-product classification but fails to escalate return cases. Run both versions repeatedly against the same tasks and graders in an isolated environment. Model outputs can vary across trials, so one successful run is not enough to accept a change. If a team changes the task or grading rubric, it records a new baseline rather than comparing the resulting score directly with the old one.

The Foundry workflows public preview describes immutable versions on saving, traces for variables and branches, and evaluators. These can link a workflow definition with its run record. The preview’s initial observability focuses on individual Foundry agents within a workflow, however, so a displayed trace is not treated as a complete record of every external action.

Reading a failure

Use both graders and traces to find why a score changed

When a candidate fails a regression task, start with the outcome. Did it escalate the return case, call the refund tool only after identity verification, and avoid finalizing an action pending approval? The final outcome cannot establish the cause, so read the trace next: did it classify incorrectly, branch incorrectly after a correct classification, or select a disallowed tool?

Graders also need verification. A code grader can quickly and reproducibly check state or parameters, but may reject a valid alternative wording. A model grader can assess explanatory quality, but is non-deterministic and needs calibration against human evaluation. Anthropic recommends keeping a known solvable reference, checking that graders are configured correctly, and reading failure traces and grades. A falling score should not immediately be treated as agent deterioration.

Acceptance conditions

Pass improvement, regression, and pending approval into one release decision

A candidate change is not accepted only because its capability score rose. Check the established regression suite, tool side effects, latency or cost, the workload handed to people, and how pending approvals are handled against the purpose of the change. A team can set the condition that a candidate improving new-product inquiries is not released if it permits a refund before identity verification.

These are organization-defined conditions, not product defaults. The value of keeping evaluations, versions, and traces is not to release more changes faster. It is to explain which change affected which established promise and who accepted any exception.
