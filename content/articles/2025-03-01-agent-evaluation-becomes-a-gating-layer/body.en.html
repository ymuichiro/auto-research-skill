Question

What should be evaluated before a prototype is treated as a deployment candidate?

Calling agent evaluation a “deployment gate” does not mean that an evaluation automatically decides whether to deploy. It means separately testing the answer, the final state changed in an environment, disallowed side effects, and a handoff to a person, so a team can explain what work may be delegated. AgentBench, GAIA, SWE-bench, and OSWorld show that different jobs have different completion conditions. This article treats them as a set of checks needed for a deployment decision, not as one overall score.

Answer contract

Can the agent use the required evidence, avoid filling gaps with guesses, and return a result in the form a user needs?

Execution contract

Did it reach an expected final state from the specified initial state using permitted actions?

Supervision contract

Can it stop dangerous actions and hand an uncertain state to a person with supporting evidence?

What benchmarks measure

“Can answer” and “can finish in an environment” require different checks

GAIA poses real-world-style questions that require reasoning, multimodal input, web browsing, and tool use. Its first version contained 466 questions and reported a comparison between human responses and GPT-4 with plugins. Its central question is whether a system can gather several kinds of information and derive a final answer. AgentBench likewise evaluates agents across environments and tools, treating performance as task-dependent.

SWE-bench builds tasks from real GitHub issues and corresponding pull requests, requiring changes to a codebase that resolve the problem. OSWorld provides real web and desktop applications, file operations, and workflows across applications with initial states and execution-based evaluation scripts. Both check a changed repository or screen state rather than a plausible explanation. BrowserGym also aims to standardize observation and action spaces across benchmarks, reinforcing that environment conditions are part of comparison.

None of these values can be transplanted directly into a deployment decision. Their value is a vocabulary for separating evaluation targets. A test of source-research correctness, a test of a saved screen state, and a test for a forbidden external action should not use the same grader if a team wants failures to be understandable.

Observation and control

Tracing and confirmation do not replace an average score; they make a failure explainable

Anthropic’s computer-use material explains that screenshot observation can miss transient notifications and that limits in speed and accuracy remain. The Operator announcement describes takeover for login, payment details, and CAPTCHAs, along with confirmation before orders and email are sent. These sources describe the design of human intervention points, not a browser-action success rate.

AutoGen v0.4 documents asynchronous messages, event-driven long-running processes, message tracing, and debugging. Building effective agents distinguishes a workflow that follows a defined path from an agent that chooses its own tool use. These features and categories do not independently prove safety or effectiveness. They do help a team decide which information to retain when investigating a failure, a stop point, or a decision passed to a person.

Evaluation card

For a calendar entry, grade the answer, saved state, and action path separately

This is a hypothetical business evaluation design. A source document supplies a deadline date and time, while a calendar has existing entries and user permissions. The expected job is to read the correct time from the document, create exactly one event in the correct calendar, and request confirmation when needed.

Answer

If the document omits a time, request clarification rather than inventing one. Connect the date and time to their source passage.

Final state

Check the calendar or API state for exactly one event in the correct calendar and time. A different calendar, time drift, a draft, and a duplicate are distinct failures.

Path and safety

Record source material, actions used, confirmation requests, and state after an error. Treat a human handoff as a correct outcome when permission is missing or a saved result cannot be confirmed.

Difficulty changes with initial data, calendar version, permitted actions, and time zone. A comparison should hold those conditions fixed while storing the score separately from the trajectory needed to investigate a cause.

Answer for deployment

Evaluation is evidence for explaining a delegation boundary, not a single pass/fail number

The “gate” in this article is not a one-step rule that deploys an agent after it passes a public benchmark. For representative work, it means defining valid answers, verified final states, forbidden side effects, and states that must be handed to a person. With those conditions in place, a team can discuss whether a prototype failure should be attributed to the model, tool, environment, or grading rule.

For early deployment candidates, choose a small number of representative cases and test the answer, execution, and supervision contracts separately. If an average score improves but an old representative case starts to create a dangerous side effect, do not pass the change. Connecting evaluation to a record of updates is the practical boundary between an impressive prototype and supervised work.
