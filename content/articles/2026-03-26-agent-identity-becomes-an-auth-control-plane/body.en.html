Knowing the agent's name does not determine its permission

Suppose an internal document-search agent also sends documents outside the organization. Recording which agent acted does not establish that the transmission was permitted. Identifying the executing software, accessing data on a user's behalf, and authorizing a particular operation are distinct decisions.

At Build 2025, Microsoft introduced an Entra Agent ID preview that assigns unique identities to agents created in Copilot Studio or Azure AI Foundry. Making agents visible as managed identities is useful. Issuing an identity, however, does not by itself determine appropriate resources and operations.

Scheduled work and user-delegated access need different permission decisions

A nightly job that writes a report to a fixed location differs from a search that must return only documents its user can read. One possible design gives the first a dedicated workload permission and makes the second reflect the user's access. This is a design example, not a claim that every platform implements these paths identically.

AWS's AgentCore announcement describes Identity supporting access to external services on behalf of users or with pre-authorized consent. That distinction is a reason to establish whether a connection serves delegated user activity or an ongoing, administratively defined job before configuring its credentials.

Conventional service accounts can also serve this purpose when separated by workload and granted narrow permissions. The problem is a shared, powerful credential that prevents operators from stopping one job independently. Evaluate a dedicated identity by whether it provides a usable unit for granting access, disabling work, and tracing activity.

Permission to reach an MCP server does not transfer to its downstream API

A delegated token is not a universal credential. The MCP 2025-11-25 authorization specification defines authorization for HTTP transports and requires servers to verify that tokens were issued for them. When an MCP server calls another API, it uses a separate token intended for that API; it must not forward the token received from its client unchanged.

In document search, the agent's access to an MCP server and that server's access to document storage belong to different connections. If storage access uses a shared permission that reads every employee's documents, authenticating the user at the entrance does not ensure that search results respect that user's permissions. The search service or storage service must apply the corresponding access conditions.

The cited flow concerns HTTP connections; it does not impose the same OAuth procedure on local standard-input/output connections. Check the actual transport and authorization design instead of inferring them from an “MCP-compatible” label.

Test access decisions separately from generated-content checks

Checking a summary for problematic language differs from deciding whether the underlying document may be read. Content inspection does not replace access control. Conversely, permission to retrieve a document does not establish that its summary is accurate or its destination is appropriate.

For a proposed document-search and external-send workflow, test both a request for an inaccessible document and an attempt to send an accessible document to an unauthorized destination. Identify which component refuses each operation and whether its records link the user to the executing agent. Explaining those two tests provides better evidence of an effective permission design than adding more identity product names.
