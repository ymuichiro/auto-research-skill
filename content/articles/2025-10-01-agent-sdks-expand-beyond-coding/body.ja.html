コードを書く仕組みを、集計や調査へ使うには

ファイルを読み、必要な処理を書き、実行結果を見て修正する。 この反復は、ソフトウェア開発だけでなく、CSVの集計や資料の調査にも使える。 Anthropicが2025年9月にClaude Code SDKをClaude Agent SDKへ改称した説明は、こうした用途の広がりを示している。

ただし、処理を実行する道具が増えても、業務上正しい結果の定義まで付いてくるわけではない。 本稿では、SDKによる作業の反復と、Looker MCP Serverによる指標への接続を分けて考える。 両者は代替製品ではなく、異なる課題を扱う部品である。

SDKが支えるのは、情報収集から結果確認までの反復

Claude Agent SDKの説明は、ファイルやコマンドを使う仕組みを、調査や問い合わせ対応などへ応用する例を挙げる。 中心にあるのは、情報を集め、処理を行い、結果を確かめる流れである。 SDKの名称変更だけで新しい用途の成功率が示されたわけではない。

月次レポートの作成を想定すると、CSVを読み、集計用のコードを作り、出力を検査して修正する構成が考えられる。 この場合、構文エラーがないことは最初の確認にすぎない。 対象月、欠損値、重複行、通貨の扱いが要件と一致しなければ、実行できるコードでも誤ったレポートになる。

売上の定義を、生成したコードだけに任せない

GoogleのLooker MCP Server発表は、AIがLookerのセマンティックレイヤーへ問い合わせ、Looker側がSQLを生成する構成を説明した。 セマンティックレイヤーは、売上などの指標や集計方法をあらかじめ定義する仕組みである。 既存の定義をエージェントから参照する接続手段が増えた、と読める。

例えば、社内で売上を返品控除後の金額と定めているなら、CSVの金額列を単純に足す処理とは結果が異なり得る。 既存指標を使う場合にも、選んだ指標、期間、絞り込み条件が質問に合うかは確認が必要だ。 接続できることは、質問の解釈が正しいことの保証にはならない。

まず一つのレポートで、計算と意味を照合する

この月次レポートの例では、同じ期間の確認済み集計を用意し、エージェントの出力と照合する。 一致しない場合は、元データ、指標の選択、絞り込み、計算のどこで差が生じたかを調べる。 出力を作る作業と、その出力を正しいと認める条件を、別々に用意するということだ。

最初の試行では入力を読み取り専用にし、生成物は別の場所へ保存する設計が考えられる。 必要な資料が見つからないときに推測で埋めるのか、未確認として止めるのかも決めておく。 これは本稿の検証案であり、両製品の既定動作を説明したものではない。

SDKをコーディング以外へ使う価値は、扱う用途の数だけでは判断できない。 一つの成果物について、取得、計算、確認までをどこまで繰り返せるかを確かめる。 その結果から、追加するツールと、人が引き受ける確認作業を選ぶ方が具体的である。
