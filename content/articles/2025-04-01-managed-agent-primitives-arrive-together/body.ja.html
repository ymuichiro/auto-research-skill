問い

マネージドなエージェント基盤は、どの責任を引き受け、何をアプリに残すのか

2025年3月の OpenAI の agent-building tools と Amazon Bedrock の multi-agent collaboration は、ツール実行と担当間の調整をサービスや SDK の機能として見せた。これは各社の提供範囲が同一になったという意味ではない。本稿では、研究で扱われてきた担当分割を読む補助線として AutoGen と Magentic-One を置き、実行、協調、業務責任を分けて比較する。

ホストされた実行

検索、ファイル、画面などの道具を呼び、実行環境の一部を提供する。

組込みの協調

アプリが担当、handoff、入力・出力の検査、記録を組み立てる。

業務の責任

本人性、データ権限、更新規則、例外時の承認は、基盤の外側で定義する。

提供面の違い

道具、SDK、複数担当の調整は、似た名前でも預かる範囲が違う

OpenAI の発表は、Responses API の Web search、file search、computer use と、オープンソースの Agents SDK を並べた。前者はホストされた道具を呼ぶ選択肢であり、後者はエージェント設定、handoff、guardrail、trace をアプリへ組み込むための部品である。SDK を使っても、アプリの配備、利用者認証、業務データの保持、外部操作の許可をサービス側が自動的に管理するわけではない。

Bedrock の一般提供は、supervisor が仕事を複数の collaborator に分ける構成と、単純な依頼を直接振り分ける構成を示した。分担の一部をサービス設定に置けても、担当の説明、外部 API の意味、誤った振り分けの扱いは利用側が決める。Building effective agents が workflow と agent を分けるのと同じく、管理された部品の有無より、どの経路を固定するかが設計上の問いになる。

研究との対応

担当分割は、機能を増やすためではなく、責任を追える形にするために使う

AutoGen は複数エージェントの会話をアプリ構築の枠組みとして扱い、Magentic-One は複雑な仕事で役割を調整する構成を研究した。これらは特定のマネージド基盤の性能を証明しない。一方で、planner、専門担当、統合役という役割を置くなら、入力、出力、失敗、終了条件を担当ごとに決める必要があることを明らかにする。

BrowserGym や Operator のような画面操作の資料は、外部環境へ作用する仕事には初期状態と完了条件が必要だと示す。バックエンド API を呼ぶ担当もブラウザを操作する担当も、外部作用の前に許可範囲と確認地点を持つ点では同じである。

想定例

製品の使い方と注文状況を答える問い合わせで、残る仕事を確かめる

以下は設計例である。製品の使い方は文書検索担当、注文状況は注文 API 担当に分ける。基盤に任せられるのは、道具の実行や担当への依頼の一部である。利用側は、誰が顧客を同定するか、どの注文を参照してよいか、API が失敗したときの回答、注文変更を許すかを定める。

検査する結果

回答の根拠、誤った担当への routing、API 失敗時の扱い、統合された回答を別々に確認する。

記録する境界

実行環境、入力と出力、権限確認、trace、利用者へ返した未確認状態を残す。

人が決めること

顧客情報の範囲、返金や変更の承認、エスカレーション先、誤操作の復旧を業務規則として定義する。

結論

比較すべきなのは機能数ではなく、責任境界である

2025年春の発表は、実行、道具、複数担当の調整を選べる基盤が増えたことを示した。ここから導ける実務上の結論は、基盤が「すべてを管理する」と捉えないことだ。ホストされた道具、アプリへ埋め込む協調、組織が保持する認証・方針・承認を分ければ、どの部品を使うかを仕事の責任に沿って選べる。
