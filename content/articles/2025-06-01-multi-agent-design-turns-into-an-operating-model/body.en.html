Question

Why should multi-agent work be designed as an operating model rather than a role diagram?

Adding roles does not create coordination. A system needs dependencies on earlier work, inputs and evidence passed in a handoff, someone to integrate and verify results, and conditions to stop or return work to a person. Azure AI Foundry Agent Service, Responses API updates, and Semantic Kernel orchestration in May 2025 treated such components as implementation and operational concerns. This article uses “operating model” to mean a design that makes work reproducible, auditable, and stoppable, not a set of role names.

Dependencies

Separate work that can run in parallel from work that must wait for earlier evidence.

Handoffs

Pass inputs, sources, unresolved points, and permission scope, not a summary alone.

Integration and stopping

Decide who checks conflicts and what counts as completion, return, or human handoff.

Scope of the published material

Coordination features enable role separation; they do not guarantee sound operation

Azure AI Foundry material, Responses API updates, and Semantic Kernel orchestration document components for agents, tools, execution records, and flows across roles. Google multi-system agents and A2A address work handed to another system. They do not establish that an organization’s roles, permissions, and quality criteria already exist.

Magentic-One and tau-bench show that work involving several tools, roles, or a user has meaningful intermediate paths as well as outcomes. Their benchmarks should not be substituted for an organization’s performance; they support the design implication that dependencies, state, and user negotiation must be evaluated.

Hypothetical example

For a research report, define what passes between collection, writing, and review

This is a design example. A collection role returns primary-source URLs, publication dates, relevant passages, and unresolved points. A writing role drafts from that evidence; a review role checks the relation of claims to sources, outdated material, and speculative language. Collection can run in parallel, but a conclusion waits for evidence. A review finding that evidence is insufficient returns work to collection rather than ending it.

A short summary alone is insufficient for this flow. Pass sources, citable facts, author interpretation, and unresolved conditions separately. An integrator resolves conflicts and a person makes the final publication decision. For a small report that one role can finish, the cost of handoffs outweighs the benefit, so it should remain a single-role task.

Conclusion

The value of multiple agents lies in being able to stop and inspect work, not in the number of workers

Making a role design an operating model means recording dependencies, handoffs, integration, and stopping conditions, rather than merely parallelizing steps. Platforms can help implement this. Quality, authority, approval, and responsibility for exceptions remain with the application and organization. Start with a single-role baseline, then add roles only where division improves time, error handling, or supervision.
