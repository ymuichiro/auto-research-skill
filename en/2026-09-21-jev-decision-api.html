Will LLMs replace every if statement? Jev and the case for a decision API

Jev is TypeSafe AI's decision model for closed choices and probabilities. This article compares it with fine-tuned classifiers, generative LLMs, and Structured Outputs, then defines the conditions for putting ambiguous judgments safely into software.

AI Strategy September 21, 2026
LLMClassificationAI ArchitectureEvaluationAI Agent

Why call an LLM when no one needs prose?

“Is this message a refund request?” “Does this contract contain an auto-renewal clause?” “Should this transaction go to human review?”

These are ordinary questions for business software.

The system needs a decision that branches the next step, not an explanation or a proposal.

Yet implementations often pass the question to a general-purpose LLM, ask it for prose or JSON, and use the result to decide what happens next.

That is not always excessive.

A generative model is appropriate when the system must explain a case, ask for missing information, or handle exceptions in language.

But when it only needs to choose from a closed set, a different question remains: why use a text-generation model when no one needs text?

Jev, released in early access by TypeSafe AI on September 15, 2026, starts from that question. TypeSafe AI's announcement says that Jev takes a state and typed questions, then returns a choice, score, or truth value with structured probabilities rather than prose.

This article calls the layer it proposes a decision API.

That is not an established industry category.

It is this article's term for a component that reads natural language but returns a decision from an application-defined answer space, separate from models that generate, calculate, or execute.

Fine-tuned classifiers and general LLMs left a practical gap

It would oversimplify history to say that BERT and LLMs were the only choices.

Zero-shot text classification has long been researched, and a 2019 benchmark evaluated classification without task-specific labelled data. Yin et al.

Even so, production designs have often chosen between two work patterns.

Fine-tuned classifier

Define labels, collect and annotate data, evaluate, then deploy. BERT showed how a pretrained representation plus a task-specific output layer can be fine-tuned for downstream work. The BERT paper

General-purpose generative LLM

Answer a new question from instructions at call time. It can combine generation, explanation, and reasoning across conditions in one call, but even a bare judgment becomes a call to a generative model.

Jev's decision API

Send a state and closed questions; receive a choice, score, or truth value with probabilities. The application constrains the model's freedom to a defined decision space.

This is not a performance ranking.

Handwritten rules still fit exact conditions; generative work still needs a generative model; and a trained model can remain the best choice where it is accurate enough.

Jev's move is not to declare either extreme smarter. It treats a distinct kind of branch as its own call: one that must read natural language but does not need to return open-ended language.

Jev receives closed decisions through three primitives

Jev's HTTP API accepts application state and a map of questions, then returns one answer per question. API reference

The application chooses each question identifier; the model receives the question, candidate options, and criteria.

Choice

Select one defined option. It fits a decision such as routing a message to refunds, technical support, or sales, and returns a probability for every option plus confidence. Choice reference

Score

Assess a state on a predefined ordered rubric. It fits judgments with order between options, such as severity or urgency. Score reference

Noul

Ask a yes-or-no question and receive the probability that it is true. It fits a binary judgment such as whether a message asks for a refund. Noul reference

Viewed only at this level, the system naturally resembles a classifier.

But the application can supply the answer space and criteria at call time.

Changing today's taxonomy from refund / support / sales to tomorrow's taxonomy with abuse becomes a change to questions and evaluation cases, rather than automatically the start of retraining.

That mutability makes Jev look less like a fixed classifier and more like a product that moves part of classifier construction into an API.

Structured Outputs competes on more than output shape

The objection that a low-cost LLM with Structured Outputs can return the required JSON is correct.

OpenAI Structured Outputs conforms model output to a developer-supplied JSON Schema, which is powerful when an application must not receive malformed output. OpenAI's announcement

Format alone, therefore, cannot justify choosing Jev.

Schema-valid JSON and a decision that is correct about the world are different properties.

The two paths are clearer when separated this way.

Generative LLM with Structured Outputs

Use a general model as a response system with a prescribed shape. If explanation, exception handling, extraction, or reasoning is needed, they can share one model call.

Jev

Make a closed judgment the API contract from the start, returning probabilities and confidence for its options. It cannot be used to generate the explanatory prose.

TypeSafe contrasts sequential LLM generation with Jev's parallel evaluation of many questions against the same state. Introduction

Its workflow evaluation also assumes decomposed questions and control by code. Workflow evals

That evaluation uses a vendor-authored harness and consensus labels from external models.

TypeSafe notes the possible bias from the people who created the harness, so its speed and cost claims cannot stand in for an independent accuracy comparison.

Jev need not be chosen because it is “smarter.”

It has a design fit when the system wants to give up generative freedom and treat candidates and probabilities as first-class inputs to software.

Removing task-specific training does not remove decision design or evaluation

Calling Jev a classifier that works without training is an effective shorthand.

The adopting company need not begin with a task-specific weight update.

But it would be wrong to read that as “write a requirement and call the API, and classification is done.”

The responsibility of classification moves into application-defined labels, criteria, thresholds, and exceptions; it does not disappear.

Changing a fine-tuned classifier

Turn requirements into label definitions, collect and annotate data, train and evaluate, then deploy. A new label changes that machine-learning workflow.

Changing a decision API

Turn requirements into questions and criteria, build evaluation cases for ordinary and boundary inputs, then specify action thresholds and human handoffs. A new label changes the questions, evaluation, and branching rules.

The second path does not eliminate machine-learning operations.

It can remove task-specific data collection and retraining as a prerequisite for the first deployment.

In exchange, someone must define what belongs in abuse, which misclassifications are unacceptable, and which answers must go to a person, with those decisions traceable in code and evaluation records.

Probability is not an automation permit, either.

Neural-network probabilities can be miscalibrated, and calibration is not a guarantee that an individual answer is right. Guo et al.

TypeSafe's documentation makes the same distinction: calibration is a property across groups of predictions, not a guarantee for one answer. System One reference

Probability feeds an if statement; it does not replace one

A decision API should not connect a model result directly to an external action.

Refunds, identity checks, transfers, and publication carry different costs of error, so they need different evidence and action conditions.

In this hypothetical routing example, the model proposes a queue while the program checks required records, confidence, and permissions in sequence.

if missing_required_record(ticket):
    route_to_human(ticket)
elif decision.confidence < ROUTING_THRESHOLD:
    route_to_human(ticket)
elif decision.choice == "refund":
    open_refund_review(ticket)
else:
    route_to_support_queue(ticket, decision.choice)

This is a design example, not a deployment report.

The model reads the message.

The program decides what may proceed automatically and what returns for review.

TypeSafe likewise illustrates routing a request to deterministic code, a specialist LLM, or a person, sending low confidence or high complexity back to a human. Intent routing reference

For high-risk actions, a plausible classification is less important than branches that can stop, deterministic checks before the action, and an auditable record.

With that division of responsibility, AI is not a free agent at the center of the application. It becomes a fuzzy if statement invoked many times inside the program.

Define the stopping conditions before measuring accuracy

Jev's type safety does not guarantee semantic safety.

The public documentation for Jev 1.13 lists numerical calculation, date comparison, multi-step indirection, long inputs with irrelevant material, and adversarial content as failure modes. Text generation is also out of scope. Known limits of Jev 1.13

The comparison for an adoption decision is therefore not Jev alone.

Handwritten rules, an existing fine-tuned classifier, a general LLM with Structured Outputs, and human review must be compared against the same evaluation set.

  • Include out-of-scope, contradictory, ambiguous, and adversarial inputs alongside ordinary cases.
  • Measure separately the cost of approving an incorrect case and the cost of sending too many cases to people.
  • Audit high-confidence answers by sample; when errors appear, update the question, criteria, threshold, or rule.
  • Because a model update can change answers, pin versions when thresholds have been tuned and re-evaluate on change. Models reference

Research on selective classification has long addressed the trade-off between error risk and the share of cases a system decides automatically. Geifman and El-Yaniv

Jev's probabilities and confidence may make that trade-off easier to implement.

The appropriate threshold and scope, however, are not choices a product can set uniformly.

The durable question is whether decisions become software components

It is too early to know whether Jev itself will win over the long term.

Immediately after an early-access release, the vendor's evaluation is not an independent comparison across general LLMs, existing classifiers, and business data.

Yet schema-constrained LLM output, zero-shot classification, and confidence-based rejection already existed as separate techniques.

Jev puts them into a product contract: read state, return closed decisions and probabilities, and let code determine action.

If that contract takes hold, AI will enter not only chat interfaces and autonomous agents, but also small branches for routing a request, judging a document, estimating risk, and sending a case back for confirmation.

Jev is interesting not because it makes one model universal.

It gives a design home to work that is lighter than generative AI and less fixed than a conventional classifier: a decision API.
