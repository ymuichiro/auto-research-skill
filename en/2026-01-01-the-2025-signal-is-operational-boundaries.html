The responsibility boundaries visible in 2025 agent development

A2A, Claude Agent SDK, and Foundry workflows expose different components for handing off work, iterating execution, and defining and evaluating paths. A research-publication scenario locates the meaning of a request, execution record, and publication approval.

AI Agents January 1, 2026 Updated September 20, 2026
AI AgentRoundupOperationsStrategy

A lens on 2025

Which responsibilities do connection, execution, and review take on?

In 2025, public materials appeared for handing work between agents, embedding an execution loop in an application, and defining and evaluating multi-step work. Taken together, they make more visible not only what an agent can do, but also where a request’s meaning, the history of execution, and responsibility for an external result belong.

This is not a measurement of 2025 adoption rates or an industry-wide competitive shift. It reads three public materials—the June transfer of A2A to the Agent2Agent project, the September Claude Agent SDK announcement, and Foundry Agent Service’s November multi-agent-workflows preview—as components that address different responsibilities. The article’s interpretation is that explicitly designing these boundaries is a prerequisite for deciding what portion of work to delegate.

Three public materials

Handing work off, iterating execution, and reviewing a path are separate problems

The June 23, 2025 A2A announcement said Google would transfer the specification, SDKs, and developer tools to the Linux Foundation’s Agent2Agent project. A2A aims to provide a common communication mechanism through which distinct agents can discover capabilities, exchange information, and coordinate work. It addresses the connection boundary: who has which capability, and in what form a request or result can pass between them.

The September 29 Claude Agent SDK announcement describes an execution loop that gathers context, acts, verifies work, and repeats. It combines files, commands, tools, and subagents so one worker can change its procedure after intermediate observations. It addresses the execution boundary: how a worker progresses with permitted tools and which result feeds the next iteration.

The November 25 Foundry workflows announcement presented diagram and YAML path definitions, variables, saved versions, execution tracing, and evaluators as a public preview. These are components for reviewing which steps run in which order, which input selects a branch, and what to evaluate. The three materials are neither a linear product generation nor equivalent choices with the same maturity.

The connection boundary visible through A2A

It is a communication mechanism for common discovery, requests, and results. A protocol alone does not define what a business-complete state means or who accepts the received artifact.

The execution and review boundaries visible through SDKs and workflows

An SDK can embed a worker’s iteration, while a workflow handles paths, run records, and evaluation. The application and organization decide which tools are allowed and which records support a publication decision.

Scenario

From a research request to publication, divide responsibility across four records

This is a scenario from this article. An editor asks for a sourced draft on how a proposed regulation could affect domestic retailers. The request sent to the researcher includes the country, time period, permitted kinds of primary material, output format, and the condition to return an item as unverified when sources cannot be found. When work passes to another agent, a mechanism such as A2A could carry that request and its result. A received state, however, is not evidence that every required source was examined.

The research worker then reads permitted material, records dates and cited passages, compares them with claims in the draft, and searches again when support is missing. The loop described by Claude Agent SDK is material for composing that retrieve, act, and verify path. The business rules remain outside the SDK: which source qualifies as primary evidence, when an unavailable source stops the work, and who confirms generated prose.

Finally, a workflow definition such as Foundry’s can make the path through research, fact review, editing, and publication review visible, along with the draft, evidence list, and unresolved items passed at each step. A run record shows which branch one article followed; an evaluation checks items such as the presence and format of citations. Publication approval is a fourth, separate record. Only when an editor has reviewed the evidence list, unresolved items, and version should the publishing action run. This scenario is not a recommendation to adopt all three products together or a reported deployment.

What completion means

Completion is a combination of contract, execution, review, and approval—not a communication state

In this scenario, the request contract defines what counts as research work. The execution record shows which material was read, where a gap appeared, and which draft resulted. The evaluation result supplies evidence against the stated format and citation conditions. The approval record shows who accepted which version for publication. Reducing all four to “complete” confuses a successful handoff, a generated draft, a passed check, and external publication.

The separation is not solely a way to limit agent autonomy. It makes it possible to know which record supports stopping for missing material, returning only fact review for correction, or identifying a published version. This article interprets the distinct 2025 announcements as exposing components for designing that separation across connection, execution, and review.

Conditions where this does not apply

Not every job needs all three components

When one worker creates a short draft without handing work to another agent, cross-agent communication such as A2A is unnecessary. A fixed calculation that runs once may be better served by an ordinary program than an SDK designed for a long iteration. An internal note that is not published may not need a publication-approval path.

These public materials describe functions and goals; they do not measure the success of an operating model that combines protocol, execution loop, and workflow evaluation. The design question is not how many components to adopt. It is where an actual job will put the request’s meaning, permission, stopping condition, and final responsibility.
