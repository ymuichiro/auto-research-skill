Research Signal

Why AI-agent comparison turned to measurable work design

Compare ReAct, Toolformer, WebArena, SWE-bench, and OSWorld to show why agent evaluation needs conditions for completing work in an environment, not just evidence of a tool call.

AI Agents January 1, 2025 Updated September 20, 2026
AI AgentRoundupBenchmarkTool Use

Question

Why can’t an AI agent be compared merely by whether it can use a tool?

Research published by January 1, 2025 had made a tool call or a one-shot response an insufficient unit of evaluation. ReAct and Toolformer study ways to incorporate outside information and APIs into action. WebArena, SWE-bench, and OSWorld evaluate whether work is completed inside an environment. This does not prove that an entire market had changed at once. It does show a set of components for measuring tools, environments, and completion conditions in comparable forms.

Select an action

Decide whether to retrieve information and which API and arguments to use.

Change an environment

Read the state of a screen, repository, or dataset, then execute several actions in sequence.

Verify completion

Judge final state, supporting evidence, and disallowed side effects against conditions for a specific job.

Action design

ReAct and Toolformer approach the same phrase, “tool use,” from different directions

ReAct interleaves reasoning traces with task-specific actions and uses observations in later decisions. Its question-answering examples sequence Wikipedia search, lookup within a page, and an action that commits to an answer. The paper establishes that a model can acquire outside information during a task and leave a trajectory that a person can inspect. It evaluates particular benchmarks; it does not establish that adding external search improves every kind of question.

Toolformer proposes a self-supervised method for learning which API to call, when to call it, which arguments to pass, and how to incorporate a result into later generation. Its tools include a calculator, question answering, search, translation, and a calendar. It is not a replacement implementation recipe for ReAct. ReAct addresses the loop between reasoning and observation, while Toolformer addresses incorporating API calls into training. Reducing both to one success metric would hide that difference.

What the sources establish

Tool-use design contains separate questions about selection, arguments, and use of an observation. A successful call is not evidence that the subsequent work is complete.

Completion conditions

Environment benchmarks made final state, rather than an answer alone, the object of evaluation

WebArena provides functioning web environments for e-commerce, forums, collaborative software development, and content management, then evaluates functional completion over long action sequences. In the April 2024 version of the paper, its best GPT-4-based agent reached 14.41% end-to-end task success while humans reached 78.24%. Those values belong to WebArena’s environment, tasks, and baseline at that time. They cannot be reused as a success rate for a company’s website automation or as a statement about current models.

SWE-bench supplies a codebase and issue description for 2,294 real GitHub issues and their corresponding pull requests across 12 Python repositories. The work resembles reading a problem, changing related files, and checking the final state with tests, rather than proposing a code fragment. OSWorld places 369 tasks in real computer environments spanning Ubuntu, Windows, and macOS, with initial-state configuration and execution-based evaluation scripts. Its reported comparison of 12.24% for the best model and 72.36% for humans is likewise an environment-specific measure that includes GUI grounding and operational knowledge.

The public version of BrowserGym aimed to put several web-agent benchmarks under shared observation and action spaces and to make experiment management more consistent. Across these efforts, the common lesson is that evaluating an agent requires more than an input prompt: the initial state, permitted actions, and completion checker must be explicit.

Product surface

Official building features supplied components for implementing a work boundary, not measurement by themselves

The 2024 update to Amazon Bedrock Agents included action groups, simplified configuration, return of control to an invoking application, and Infrastructure as Code. Vertex AI Agent Builder and Claude tool use likewise documented options for composing applications that connect knowledge sources and external functions. Vendor documentation alone does not guarantee that a user’s work has been completed correctly.

These components can nevertheless make a chosen work boundary easier to implement. A team can specify allowed APIs, the point at which control returns to its application, and the sources that may be consulted as configuration rather than only as model instructions. The distinction between workflows and agents in Building effective agents is also a useful design reference for choosing a degree of control that fits the work, instead of presuming universal autonomy.

Make it concrete

For “find the maintenance deadline in internal documents,” write the scorecard first

The following is a hypothetical application of the research, not a reported deployment. A user asks for a device’s maintenance deadline and an agent searches internal documents. An API response is insufficient. A document for an older model is the wrong evidence even if the operation succeeded. If the deadline depends on model number or contract, generating a plausible date is not completion either.

Inputs and permitted actions

Specify a model number, contract identifier, and searchable document repositories. Do not include external delivery or contract changes in this job.

Evidence of completion

Return the applicable document version, the passage stating the deadline, and its correspondence to the contract. Treat “unknown because evidence is missing” as a correct outcome when appropriate.

Records to compare

On the same set of questions, record answers meeting the conditions, evidence mismatches, time, and call count. Aggregate these separately from raw API success.

This scorecard does not import a research benchmark score into an organization. It is a design example for spelling out local initial and final states, as environment benchmarks do for their own tasks.

Design conclusion

Measurable work is needed to make failures legible, not to make a demo smaller

The most useful implication of the early-2025 research and product material is to avoid comparing agents through a list of apparent capabilities. Separating tool selection, actions in an environment, and final state makes it possible to tell whether a search chose the wrong document, an operation stopped partway through, or the completion condition was vague. This article calls that separation measurable system design.

A benchmark success rate or a documented product feature still cannot be generalized directly into an organization’s business outcome. Start with work whose source boundary and final state are easy to specify and whose external side effects are limited. Then use recorded failures to revise permitted actions and completion conditions. That is how a striking demo can become work that an organization can operate.
